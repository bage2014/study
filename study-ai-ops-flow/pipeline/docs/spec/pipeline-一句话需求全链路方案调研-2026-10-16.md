# 方案调研报告：AI 一句话需求到自动发布全链路流水线

## 调研信息

| 项目 | 内容 |
|------|------|
| 调研主题 | 一句话需求 → 自动生成代码 → 自动 Review → 自动测试 → 自动打包 → 自动发布 |
| 调研范围 | 3+ 互联网大厂方案、2+ 业界方案，与现有自研方案（ai-ops）对比 |
| 创建日期 | 2026-10-16 |
| 版本 | v1.0 |

## 调研目标

验证是否有优于当前自研方案（Temporal Workflow + 多 LLM Agent 分阶段编排）的实现方式，为 ai-ops 演进提供决策依据。

## 候选方案

| 方案 | 来源 | 类型 |
|------|------|------|
| A. AWS Kiro | Amazon（大厂） | Spec 驱动 Agentic IDE |
| B. GitHub Copilot Coding Agent | Microsoft/GitHub（大厂） | Issue-to-PR 云 Agent |
| C. 腾讯 CodeBuddy | 腾讯（大厂） | 全流程 AI IDE + CLI |
| D. 阿里 Qwen Code / Qoder | 阿里（大厂） | 终端 Agent + 多 Review Agent |
| E. Cognition Devin | 业界（标杆） | 自主软件工程师云 Agent |
| F. OpenHands | 业界（开源） | 事件流 Agent 平台 |
| G. 自研（现状） | 本项目 | Temporal + 多 Agent 分阶段流水线 |

## 方案详细分析

### 方案 A：AWS Kiro —— Spec 驱动（Spec as Source of Truth）

| 项目 | 内容 |
|------|------|
| 核心模式 | 一句话 → `requirements.md`（用户故事+验收标准）→ `design.md`（架构设计）→ `tasks.md`（任务清单）→ 逐任务实现与验证 |
| 关键机制 | **Steering files**（项目约定/架构约束的 Markdown，每次生成时注入）；**Agent Hooks**（文件保存/提交时自动触发 lint、测试生成、安全扫描、文档更新）；**Autonomous Mode**（委托目标，自动规划→编码→开 PR） |
| 优势 | Spec 三件套沉淀在仓库中，决策可追溯；约定约束（steering）从"提示词约定"升级为"环境强制"；hooks 让质量卡点自动化而非靠 Review 英雄主义 |
| 不足 | 强绑定 Kiro 生态；发布环节依赖外部 CI/CD，本身不做部署编排 |
| 对本项目的借鉴 | **Steering files ≈ 我们的 `.pipeline-convention.yaml`**；tasks.md 清单化 ≈ 我们的 TASK_SPLIT；hooks 思想可引入"测试失败自动重跑" |

### 方案 B：GitHub Copilot Coding Agent —— Issue 即工单、PR 即交付

| 项目 | 内容 |
|------|------|
| 核心模式 | 将 Issue 指派给 Copilot → 云沙箱中规划→编码→跑测试→开 Draft PR → 人审合并；打包/发布由 GitHub Actions 承接 |
| 关键机制 | **Automations**（定时/事件触发 Agent：每晚修复失败测试、每周生成发布说明）；**Agentic autofix**（对 CodeQL 扫描告警自动修复并重跑扫描验证，2-4 分钟）；MCP 扩展工具链 |
| 优势 | 与 GitHub 生态原生融合（Actions = 打包发布、CodeQL = 安全卡点、PR Review = 人工门禁）；"Agent 干粗活 + 人做门禁"的治理模型清晰 |
| 不足 | 需求侧无结构化拆解（一句话直接进 Issue）；强依赖 GitHub 平台 |
| 对本项目的借鉴 | **测试失败自动修复循环**（我们已实现 autoFixOnTestFail）；自动修复后**重跑原分析器验证**才提 PR，比"只改不验"更可靠 |

### 方案 C：腾讯 CodeBuddy —— 产设研部一体化

| 项目 | 内容 |
|------|------|
| 核心模式 | 自然语言 → 结构化 PRD → 设计稿 → 前后端代码 → 一键部署到 CloudStudio/EdgeOne |
| 关键机制 | 需求-设计-开发-部署四阶段流水线；内置 BaaS（Supabase/CloudBase 自动处理数据库与鉴权）；IDE + CLI 双形态 |
| 优势 | 全链路最完整（含部署环节，开箱即用）；组件库（TDesign 等）约束前端生成质量 |
| 不足 | 部署目标绑定腾讯云生态；代码 Review 与质量卡点能力弱于 A/B；复杂存量代码库适配有限 |
| 对本项目的借鉴 | **部署策略可插拔**（Local/Docker/K8s/云厂商）方向一致；BaaS 兜底降低"缺数据库就失败"概率 |

### 方案 D：阿里 Qwen Code / Qoder —— 对话式需求澄清 + 并行多 Review Agent

| 项目 | 内容 |
|------|------|
| 核心模式 | 一句话 → AI 主动反问补全需求细节 → 生成需求文档 → 人工确认 → 自动化搭建；`/review` 启动 9 个并行 Review Agent（安全/性能/质量多维度）并自动修复 |
| 关键机制 | **需求反问澄清**（不急于写代码，先聊透）；**9 Agent 并行审查 + 一键修复 + linter 复验**；Qoder Quest 引擎自动拆解复杂需求；10 万+ 文件仓库索引 |
| 优势 | 需求澄清环节是"一句话需求"场景的关键短板补丁（与我们 brainstorming 技能同思路）；多维度并行 Review 全面 |
| 不足 | 打包/发布环节缺失；企业落地依赖阿里云百炼 |
| 对本项目的借鉴 | **REQUIREMENT_ANALYSIS 阶段加入"反问澄清-人工确认"回环**（我们已有 approval 机制，可直接复用）；Review 维度细分并行 |

### 方案 E：Cognition Devin —— 全自主云 Agent（业界标杆）

| 项目 | 内容 |
|------|------|
| 核心模式 | 自然语言任务 → 隔离 microVM（自带 shell/编辑器/浏览器）→ 规划→编码→浏览器实测→修复迭代 → merge-ready PR；可从 CI/Jira/Slack/API 触发 |
| 关键机制 | 自带浏览器**端到端实测**（点击验证自己构建的功能并录像）；模型无关路由（按任务选最优模型，Fusion 降本 60%）；每 Agent 独立 VM，动作全审计；67% PR 合并率 |
| 优势 | 自治度最高，验证手段最强（录屏自证）；治理模型完善（人审门禁、审计轨迹） |
| 不足 | 闭源 SaaS，成本按任务计费；部署发布仍交给外部 CI/CD；最佳适配 junior 级任务 |
| 对本项目的借鉴 | **测试执行阶段加 UI 自验**（我们已在 UI 测试引入 Playwright，方向一致）；"不验证不开 PR"的纪律 |

### 方案 F：OpenHands —— 开源可自托管 Agent 平台

| 项目 | 内容 |
|------|------|
| 核心模式 | 事件流架构（agent/runtime/event stream 三层分离）→ Docker 沙箱内写代码、跑命令、浏览网页 → 完成任务；原生集成 GitHub/GitLab/Slack/Jira/CI |
| 关键机制 | CodeAct 统一动作空间（可执行代码即动作）；LiteLLM 模型无关路由；沙箱化执行保障安全；SWE-bench Verified 77.6% |
| 优势 | MIT 开源可自托管，无供应商锁定；沙箱执行天然隔离；可作为"代码生成与自修复"环节的执行引擎嵌入现有流水线 |
| 不足 | 不提供需求拆解/发布编排，是"执行引擎"而非"全流程编排器"；企业级管控在收费层 |
| 对本项目的借鉴 | **可作为 CODE_GEN 阶段的 Activity 执行后端**：Temporal 负责编排（我们强项），OpenHands 沙箱负责生成+自修复+测试（它强项），分工互补 |

### 方案 G：自研现状（对照基线）

| 项目 | 内容 |
|------|------|
| 核心模式 | Temporal Workflow 编排 10 阶段（需求分析→特性拆分→任务拆分→代码生成→测试生成→审查→PR→测试执行→构建→部署），LLM Agent 逐阶段产出，人审门禁（approval），本地/Docker 可插拔部署 |
| 优势 | 全流程闭环含部署；阶段可视化、可重试、可人工干预；私有化、零许可成本 |
| 不足 | 代码生成与自修复能力受限于单模型提示词工程（无沙箱执行验证）；无需求澄清回环；无仓库级约定注入的强制力 |

## 方案推荐

### 结论：不替换，走"自研编排 + 借鉴补强"路线

**推荐理由**：
1. 大厂方案（A-D）共同短板：**发布编排要么缺失、要么绑定自家云**；且核心能力闭源，无法私有定制
2. Devin/OpenHands 证明了关键差距不在编排，而在**生成环节的沙箱执行与自我验证**——这正是我们流水线当前"假成功/编译不过"问题的根因
3. 我们的 Temporal 编排 + approval 门禁 + 可插拔部署已具备 A/B/C 的骨架，缺的是肌肉

### 借鉴补强清单（按优先级）

| # | 借鉴自 | 改进点 | 落地到本项目 |
|---|--------|--------|--------------|
| 1 | E/F | **代码生成沙箱化**：生成后必须在隔离环境编译跑通才算产出 | CODE_GEN Activity 内嵌编译验证（mvn compile 通过才写入结果），或直接接入 OpenHands SDK 作为执行后端 |
| 2 | A | **Steering/约定强制注入**：约定文件内容拼入每次 codegen 提示词 | 读取 `.pipeline-convention.yaml` 注入 CODE_GEN/TEST_GEN 提示词，解决"重复类路径"问题 |
| 3 | D | **需求反问澄清回环**：一句话需求先澄清再确认 | REQUIREMENT_ANALYSIS 产出澄清问题 → 复用 approval 机制等人确认 → 再进入拆分 |
| 4 | B | **修复后重跑原校验**：自修复循环终点是"重跑原测试/扫描全绿" | autoFixOnTestFail 已实现雏形，补充编译验证作为硬门禁（已部分完成） |
| 5 | C | **部署策略扩展**：保留 Local/Docker，预留云厂商策略接口 | DeployStrategy 已策略化，低成本扩展 |

# 变更记录：录制数据从内存迁移至 H2 持久化

| 项目 | 内容 |

| 模块 | rca-agent-backend |
| 变更日期 | 2026-10-13 |
| 状态 | 已完成 |

## 变更原因

优化报告 P1-2 项：`RecordingService` 原使用 `ConcurrentHashMap` 纯内存存储，存在三大问题：

1. **重启丢失**：服务重启后历史记录与录制数据全部丢失
2. **无容量上限**：长期运行内存无限增长
3. **多实例不共享**：负载均衡时各实例数据隔离

## 变更内容

| 变更项 | 变更前 | 变更后 |
|--------|--------|--------|
| 依赖 | 无持久化依赖 | 新增 `spring-boot-starter-data-jpa` + `com.h2database:h2` |
| 配置 | 无数据源配置 | 新增 H2 数据源 + JPA `ddl-auto: update` |
| 实体 | 纯 POJO（`AnalysisRecord` / `Recording`） | 新增 JPA 实体 `AnalysisRecordEntity` / `RecordingEntity` |
| Repository | 无 | 新增 `AnalysisRecordRepository` / `RecordingRepository` |
| RecordingService | `ConcurrentHashMap` 内存操作 | 改为调用 JPA Repository，对象序列化为 JSON 存储 |
| 单元测试 | 直接 `new RecordingService()` | 新增测试辅助类 `InMemoryRecordingService`（继承并覆盖为内存行为） |

## 技术方案

采用 **JSON 序列化 + JPA** 的轻量方案：

- `RcaRequest` / `RcaResponse` / `List<InteractionRecord>` 通过 Jackson 序列化为 JSON 字符串，存入 CLOB 字段
- 避免复杂的嵌套对象关系映射（`RcaResponse` 含 Hypothesis/Evidence/Conclusion 等深层结构），保持 schema 简洁
- 读取时反序列化还原对象，对上层（Controller / Orchestrator / 回放逻辑）完全透明，对外 API 行为不变

### 表结构

| 表名 | 字段 | 说明 |
|------|------|------|
| `rca_analysis_record` | analysis_id(PK), request_json, response_json, result_level, recorded, created_at | 分析历史记录 |
| `rca_recording` | recording_id(PK), analysis_id, interactions_json, created_at | 录制数据（与分析记录一对一） |

### 数据库配置

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:rca-agent;DB_CLOSE_DELAY=-1;MODE=MySQL
  jpa:
    hibernate:
      ddl-auto: update
```

默认使用 **H2 内存模式**（表结构由 JPA 自动建，容量与生命周期由 DB 管理）。如需文件持久化，改为：

```yaml
url: jdbc:h2:file:${user.home}/.rca-agent/db;AUTO_SERVER=TRUE
```

生产环境可将 url 切换为 MySQL（MODE=MySQL 已兼容语法），实体与代码无需改动。

## 风险评估

| 风险项 | 风险等级 | 缓解措施 |
|--------|----------|----------|
| JSON 序列化/反序列化失败 | 低 | Jackson 已注册 JavaTimeModule 处理 LocalDateTime；失败仅 log.warn 并跳过该条，不影响主流程 |
| 默认内存模式重启仍丢失 | 中 | 文档已说明切换文件模式 / MySQL 的方式；后续可按需启用 |
| 大对象 CLOB 读写性能 | 低 | 当前数据量可控；后续可将 interactions 拆分为独立行存储 |

## 1. 现状架构

确定性管道：**Plan → BroadScan → BroadAnalyze → FocusedScan → FocusedAnalyze → GlobalReact**

- Plan：LLM 语义分类（软降级到 RuleBasedPlanner 关键字分类），产出竞争假设
- BroadScan：Playbook 症状驱动路由工具，`parallelStream` 并发采集证据
- Analyze：EvidenceEvaluator 裁决 SUPPORT/REFUTE/NEUTRAL → HypothesisScorer 贝叶斯式置信度更新
- GlobalReact：拓扑裁剪（±N 跳）+ 变更感知（时间窗内同目标变更加权）+ 反事实验证（决定性信号覆盖率）
- 存储：RecordingService 纯内存 `ConcurrentHashMap`

---

## 2. 优化空间清单

按优先级分 P0（正确性/可信度）→ P1（可扩展性）→ P2（性能/工程化）。

### P0-1 基线由 mock 常量写死，无真实历史基线

**现状**：`MockToolCatalog` 每个指标的 baseline / threshold / abnormal 均为硬编码常量，`MockMcpTool` 按场景直接返回正常值或异常值。

**问题**：
- 无法验证"偏离基线"计算在真实数据上的准确性
- demo 演练时指标波动完全由代码决定，与真实监控行为脱节

**优化方向**：
- 基线改为时间窗滑动统计（如过去 7 天同时段 P50/P95），接入 demo 服务的真实 Actuator 指标
- 或至少支持从配置/文件加载基线模板，便于不同场景复用

**参考**：业界标准做法为「同比/环比基线 + 3-sigma 或 IQR 异常检测」。

---

### P0-2 置信度模型过于简化，无时间衰减与证据独立性处理

**现状**：`HypothesisScorer` 公式 `belief = support / (support + 1.2*refute + 0.5)`，`confidence = 0.35*prior + 0.65*belief`。

**问题**：
- 同一工具连续多次上报的证据被独立累加，证据间相关性未建模（如 `db_slow_query` 与 `db_cpu` 高度相关，会重复计权）
- 证据无时间衰减：告警时刻的异常与 30 分钟前的异常等权
- 先验固定 0.35/0.65 比例，无法随证据量自适应（证据少时应更依赖先验）

**优化方向**：
- 引入证据相关性分组（按 layer/targetType 聚类，组内取 max 而非 sum）
- 时间衰减因子 `w = exp(-λ * minutesBeforeAlarm)`
- 先验权重随证据量动态调整（如 `α = priorStrength / (priorStrength + evidenceCount)`）

---

### P0-3 拓扑图为硬编码 mock，无真实服务发现

**现状**：`TopologyService.buildGraph()` 手写死 `appId + "-db" / "-redis" / "-mq" / "-host"` 及 `supplier-api`，另加噪声子图。

**问题**：
- 真实微服务拓扑远比这复杂（多级依赖、共享中间件、跨团队服务）
- 硬编码导致拓扑裁剪在真实场景下失效，±N 跳计算无意义

**优化方向**：
- 短期：拓扑改为配置驱动（YAML/DB 维护服务依赖关系）
- 长期：接入服务注册中心（Nacos/Eureka）+ APM trace 数据自动构建实时拓扑
- 拓扑图增加边权重（调用量/错误率），支持加权 BFS

---

### P0-4 反事实验证覆盖率低时惩罚力度固定，无分级

**现状**：`GlobalReactService` 反事实验证 `coverage < 0.5` 时统一扣 0.15。

**问题**：
- coverage=0.49 与 coverage=0.01 惩罚相同，粒度太粗
- 决定性信号缺失的原因未区分（工具未采集到 vs 采集到但正常）

**优化方向**：
- 惩罚改为连续函数，如 `penalty = 0.3 * (1 - coverage)`
- 区分"信号未采集"与"信号正常"：前者不应惩罚（可能是工具不可用），后者才构成反事实
- 反事实结果在结论中显式列出缺失信号清单（当前已有 missingSignals，但未在 API 响应中透出）

---

### P1-1 工具集静态写死，无法动态扩展

**现状**：`MockToolCatalog.allTools()` 硬编码 30+ 工具，`ScanPlaybook` 的 SYMPTOM_PLAYBOOK / FOCUSED_PLAYBOOK / DECISIVE_TOOLS 均为 `Map.of()` 静态常量。

**问题**：
- 新增监控工具需改代码重启
- 不同环境（测试/预发/生产）工具集无法差异化配置

**优化方向**：
- 工具注册改为 SPI / 配置驱动：`@ConfigurationProperties` 加载工具列表，或支持数据库/配置中心动态推送
- Playbook 路由规则外置为 JSON/YAML，支持热更新
- 保留 `@PostConstruct` 校验机制，但校验对象改为动态加载后的注册表

---

### P1-2 录制数据纯内存存储，无持久化与生命周期管理 ✅ 已解决（2026-10-13）

> 已通过 [CL-20261013-01](../changelog/rca-agent-录制数据H2持久化-2026-10-13.md) 落地：改为 JPA + H2 持久化（JSON 序列化存 CLOB），新增 `AnalysisRecordEntity` / `RecordingEntity` 与对应 Repository；默认内存模式，可切换文件模式或 MySQL。

**现状（变更前）**：`RecordingService` 用 `ConcurrentHashMap` 存 `AnalysisRecord`，重启丢失，无容量上限。

**问题**：
- 重启后历史记录与录制数据全部丢失
- 长期运行内存无限增长（PRD 中 Open Question 已标记但未解决）
- 无多实例共享能力（负载均衡时录制数据不互通）

**优化方向**：
- 持久化到 H2（开发）/ MySQL（生产），或至少序列化到本地文件（如 RocksDB/MapDB）
- 增加 TTL 与 LRU 淘汰：`@Scheduled` 定期清理过期记录，或接入 Caffeine 缓存
- 录制数据压缩存储（JSON → Protobuf/Avro），大对象（heapdump 引用）外置

---

### P1-3 并发模型粗糙，parallelStream 共用 ForkJoinPool

**现状**：`BroadScanService.scanOneHypothesis` 使用 `parallelStream()` 并发调用工具。

**问题**：
- 默认共用 `ForkJoinPool.commonPool()`，与系统其他任务争抢线程
- 无超时控制：某个工具卡住会拖垮整个 BroadScan
- 无线程池隔离：工具调用与 Web 请求线程混在一起

**优化方向**：
- 自定义 `ForkJoinPool` 或改用 `CompletableFuture` + 专用线程池（如 `rca-scan-executor`）
- 每个工具调用包裹超时（如 `CompletableFuture.orTimeout(5, TimeUnit.SECONDS)`）
- 失败工具不影响整体：当前已 `.filter(ToolResult::success)`，但需记录失败原因到 StageTrace

---

### P2-1 无指标与追踪，自身可观测性缺失

**现状**：RCA Agent 自身无 Micrometer 指标、无分布式追踪、无结构化日志。

**问题**：
- 无法知道各阶段耗时、工具调用成功率、LLM 使用频率
- 排查 Agent 自身问题时无据可依

**优化方向**：
- 引入 `spring-boot-starter-actuator` + Micrometer
- 关键指标：`rca_analysis_total`、`rca_stage_duration_seconds{stage=Plan/BroadScan/...}`、`rca_tool_call_total{tool,status}`、`rca_llm_used_total`
- 接入 OpenTelemetry， trace 贯穿整个分析流程

---

### P2-2 无 API 限流与配额管理

**现状**：`RcaController` 直接暴露分析接口，无认证、无限流。

**问题**：
- 恶意/高频调用可打满线程池与内存
- LLM 调用无配额控制，成本不可控

**优化方向**：
- 接入 Spring Security + API Key 认证
- 限流：Resilience4j RateLimiter（如 10 req/min per appId）
- LLM 调用配额：每日/每应用 token 上限，超限自动降级到规则引擎

---

### P2-3 结果可解释性可进一步增强

**现状**：结论含因果链（`buildCausalChain`），但为文本列表，无结构化图数据。

**优化方向**：
- 因果链输出结构化 JSON（节点+边），前端可直接渲染为 DAG 图
- 增加"证据热力图"：按工具/时间二维展示异常程度
- 支持导出 PDF/Markdown 报告，便于归档与分享

## 3. 优化优先级矩阵

| 优化项 | 影响 | 工作量 | 优先级 | 建议落地方式 |
|--------|------|--------|--------|-------------|
| P0-1 真实基线 | 高 | 中 | P0 | 接入 demo 服务 Actuator 指标 |
| P0-2 置信度模型增强 | 高 | 中 | P0 | 时间衰减 + 证据相关性分组 |
| P0-3 拓扑配置化 | 高 | 低 | P0 | YAML 配置替代硬编码 |
| P0-4 反事实分级 | 中 | 低 | P0 | 连续惩罚函数 + 缺失信号透出 |
| P1-1 工具动态扩展 | 中 | 中 | P1 | 配置驱动 + 热更新 |
| P1-2 录制持久化 | 中 | 中 | ~~P1~~ ✅ 已完成 | H2 持久化（[CL-20261013-01](../changelog/rca-agent-录制数据H2持久化-2026-10-13.md)） |
| P1-3 并发模型优化 | 中 | 低 | P1 | 专用线程池 + 超时控制 |
| P2-1 自身可观测性 | 中 | 低 | P2 | Micrometer + Actuator |
| P2-2 API 限流 | 低 | 低 | P2 | Resilience4j |
| P2-3 结果可视化 | 低 | 中 | P2 | 结构化因果链 + 前端 DAG |

## 4. 快速验证建议

选择 **P0-3（拓扑配置化）** 与 **P0-4（反事实分级）** 作为首批落地项：

1. **拓扑配置化**：新增 `topology.yml`，将 `TopologyService` 改为从配置加载，保持接口不变，1 天内可完成
2. **反事实分级**：修改 `GlobalReactService` 惩罚公式，将 `COUNTERFACTUAL_PENALTY` 从固定 0.15 改为 `0.3 * (1 - coverage)`，同步更新单测

两项改动均向后兼容，可通过现有 demo 服务（db_slow_query / mq_lag 等场景）回归验证。

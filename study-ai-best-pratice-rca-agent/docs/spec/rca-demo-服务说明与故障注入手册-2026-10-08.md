## 1. 背景与用途

为 RCA Agent 提供**可复现、可观测的真实故障演练靶子**：两个最小化 Spring Boot 微服务，内置故障注入接口，用于演练 OOM、请求超时级联、CPU 打满、线程泄漏、下游错误率等典型生产事故的根因分析（RCA）全流程。

设计原则：

- **零外部依赖**：无数据库 / 无注册中心 / 无 MQ，库存与订单均为内存存储，clone 即可跑；
- **故障显式可控**：所有故障通过 HTTP 接口按需注入，`/fault/reset` 一键清理；
- **观测面齐全**：内置 Actuator，暴露指标、线程栈、堆转储等 RCA 关键证据入口。

> 警告：`/fault/**` 接口仅可存在于 demo，严禁合入任何生产环境代码或暴露到生产网络。

## 4. 快速启动

### 4.1 前置条件

JDK 17+。供应服务必须先于订单服务启动（订单服务启动期不强制连通，但下单依赖它）。

### 4.2 方式一：Maven 插件

```bash
# 终端 1
mvn -pl demo-supplier-service spring-boot:run
# 终端 2
mvn -pl demo-order-service spring-boot:run
```

### 4.3 方式二：可执行 jar

```bash
mvn -pl demo-order-service,demo-supplier-service package -DskipTests

java -jar demo-supplier-service/target/demo-supplier-service-0.0.1-SNAPSHOT.jar
java -jar demo-order-service/target/demo-order-service-0.0.1-SNAPSHOT.jar
```

### 4.4 OOM 演练专用启动参数

用小堆快速触发 OOM，并自动留存堆转储作为 RCA 物证：

```bash
java -Xmx128m \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=./order-oom.hprof \
     -jar demo-order-service/target/demo-order-service-0.0.1-SNAPSHOT.jar
```

### 4.5 可配置项

| 配置 / 环境变量 | 默认值 | 说明 |
|------|------|------|
| `SUPPLIER_BASE_URL` | `http://localhost:8084` | 订单服务调用供应服务的基地址 |
| 客户端 connect-timeout | 1000ms | TCP 连接超时 |
| 客户端 read-timeout | 2000ms | 读取响应超时（超时级联的关键阈值） |

### 4.6 验证启动成功

```bash
curl http://localhost:8084/actuator/health   # {"status":"UP"}
curl http://localhost:8083/actuator/health
```

## 5. 接口清单

### 5.1 供应服务（8084）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/supply/check?skuId=&quantity=` | 正常库存查询，毫秒级返回 |
| GET | `/api/supply/slow?millis=3000` | 人为 sleep（封顶 60s），模拟慢 SQL / 慢下游 |
| GET | `/api/supply/flaky` | 约 50% 概率返回 500，模拟不稳定节点 |

内置库存数据：

| skuId | 可用数量 | 单价 |
|-------|---------|------|
| SKU-1 | 1000 | 19.99 |
| SKU-2 | 100 | 5.50 |
| SKU-3 | 0 | 99.00 |

### 5.2 订单服务（8083）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/orders` | 下单：先远程校验库存，通过后内存落单 |
| GET | `/api/orders` | 订单列表 |
| GET | `/api/orders/{id}` | 订单详情 |

下单请求体：

```json
{ "skuId": "SKU-1", "quantity": 2 }
```

### 5.3 故障注入接口（两个服务均提供）

| 方法 | 路径 | 适用服务 | 说明 |
|------|------|---------|------|
| GET | `/fault/timeout?millis=5000` | order | 调供应服务慢接口制造跨服务超时，返回 504 |
| GET | `/fault/oom?mb=10` | 两者 | 一次性泄漏指定 MB 堆内存（强引用不可回收） |
| POST | `/fault/oom/leak/start?mbPerSecond=5` | 两者 | 每秒持续泄漏，观察堆爬升 / GC 频率 |
| POST | `/fault/oom/leak/stop` | 两者 | 停止持续泄漏任务（已泄漏内存仍占用） |
| POST | `/fault/oom/clear` | 两者 | 释放全部已泄漏内存块 |
| GET | `/fault/cpu?seconds=10` | 两者 | 忙等占满一个核；并发请求可占满多核 |
| GET | `/fault/threads?count=200` | 两者 | 创建永久阻塞线程，模拟线程泄漏（单次封顶 2000） |
| POST | `/fault/reset` | 两者 | 停止泄漏任务 + 释放内存 + 中断泄漏线程 |

### 5.4 Actuator 观测端点（RCA 证据入口）

| 端点 | 用途 |
|------|------|
| `/actuator/health` | 健康状态 |
| `/actuator/metrics` | JVM / HTTP / 系统指标入口（如 `jvm.memory.used`、`http.server.requests`） |
| `/actuator/threaddump` | 实时线程栈（定位阻塞、线程泄漏、忙等） |
| `/actuator/heapdump` | 下载堆转储（MAT / jhat 分析内存泄漏） |
| `/actuator/loggers` | 动态调整日志级别 |

## 6. RCA 场景演练手册

每个场景给出：**注入方式 → 表象 → 观测点 → 根因 → 证据链**，与 RCA Agent 的「Plan → Scan → Analyze」分析路径对应。

### 场景 1：请求超时级联（跨服务）

```bash
curl 'http://localhost:8083/fault/timeout?millis=5000'
# 约 2s 后返回 504 Gateway Timeout
```

- **表象**：订单服务 504，耗时精确卡在 ~2000ms。
- **根因**：订单服务 read-timeout(2s) < 供应服务实际耗时(5s)。注意供应服务侧请求仍在执行，上游超时不会自动取消下游。
- **观测点 / 证据**：
  - 订单服务异常日志含 `SocketTimeoutException`；
  - 供应服务 `/api/supply/slow` 仍处于 RUNNABLE/TIMED_WAITING（threaddump 可证）；
  - 响应时间恒等于客户端超时阈值，是超时类故障的典型特征。

### 场景 2：堆内存泄漏 / OOM

```bash
# 方式 A：持续缓慢泄漏，观察曲线
curl -X POST 'http://localhost:8084/fault/oom/leak/start?mbPerSecond=5'
# 方式 B：配合 -Xmx128m 反复调用快速打爆
curl 'http://localhost:8083/fault/oom?mb=50'
```

- **表象**：堆使用量单调爬升不回落，Full GC 频繁且回收无效，最终 `java.lang.OutOfMemoryError: Java heap space`。
- **根因**：`FaultInjector` 用静态集合强引用持有 byte[]（等价于"缓存只加不清"）。
- **观测点 / 证据**：`/actuator/metrics/jvm.memory.used`、GC 日志、`/actuator/heapdump` 导出后用 MAT 查看支配树，定位大量 `byte[]` 被静态集合引用。

### 场景 3：CPU 打满

```bash
# 单核；开多个终端并发调用即可打满多核
curl 'http://localhost:8084/fault/cpu?seconds=30'
```

- **表象**：CPU 使用率 100%，服务响应变慢（Tomcat 工作线程被抢占）。
- **根因**：无 I/O 的纯计算忙循环。
- **观测点 / 证据**：threaddump 中对应线程长期 RUNNABLE，栈顶持续停留在 `FaultInjector.burnCpu`；多次采样栈顶不变即为 CPU 热点。

### 场景 4：线程泄漏 / 线程数膨胀

```bash
curl 'http://localhost:8084/fault/threads?count=500'
```

- **表象**：线程数持续增长不回落；极端情况触及进程 / 系统线程上限，出现 `unable to create new native thread`。
- **根因**：创建的线程永久阻塞且无人回收（等价于线程池任务卡死、线程只增不减）。
- **观测点 / 证据**：`/actuator/threaddump` 中大量 `fault-leaked-thread-*` 处于 TIMED_WAITING；`/actuator/metrics/jvm.threads.live` 持续走高。

### 场景 5：下游错误率升高

```bash
# 连续调用观察约 50% 的 500
for i in {1..10}; do curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8084/api/supply/flaky; done
```

- **表象**：供应服务间歇性 500；订单侧若下单期间命中则返回 502（Bad Gateway）。
- **根因**：下游节点不稳定（等价于单节点故障、发布缺陷、依赖抖动）。
- **观测点 / 证据**：对比两个服务的 `http.server.requests` 指标中 4xx/5xx 计数；错误是否集中于单一下游 / 单一接口。

### 场景 6：正常业务基线（对照组）

```bash
curl -X POST http://localhost:8083/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"skuId":"SKU-1","quantity":2}'
# 200，totalAmount=39.98
```

- 库存不足返回 409（SKU-3）；参数非法返回 400。
- 用途：故障演练前后做对照，确认业务链路本身正常，缩小归因范围。

## 7. 标准 RCA 排查路径（在本 demo 上的操作顺序）

1. **定表象**：记录 HTTP 状态码、耗时特征（是否恒定卡在某个超时值）、影响面（单接口 / 全服务）。
2. **看指标**：`/actuator/metrics` 查延迟分位、错误率、堆内存、线程数、CPU。
3. **抓线程栈**：`/actuator/threaddump`，间隔采样 2–3 次对比，定位 RUNNABLE 热点或大量 WAITING 线程。
4. **导堆转储**：内存类问题用 `/actuator/heapdump`，MAT 分析大对象与引用链。
5. **顺拓扑下钻**：订单服务异常时，沿调用链检查供应服务，区分"自身故障"与"下游传导"。
6. **下结论**：根因必须锚定可复现证据（指标 / 线程栈 / 堆分析），并给出止血（如 `/fault/reset`、扩容）与根治建议。

## 8. 验收标准

| 验收项 | 标准 | 状态 |
|--------|------|------|
| 独立启动 | 两个服务无外部中间件即可启动，health 为 UP | ✅ |
| 正常链路 | 下单 / 查询 / 库存不足 / 参数校验行为正确 | ✅ |
| 超时级联 | `/fault/timeout` 在 ~2s 返回 504 | ✅ |
| OOM | 持续泄漏可复现堆爬升与 OOM，heapdump 可用 | ✅ |
| CPU / 线程 | 故障注入后指标与 threaddump 有明确对应证据 | ✅ |
| 故障清理 | `/fault/reset` 后内存与线程恢复 | ✅ |

## 五大分类 + 14 风格一览表

| 类别 | 风格 | 核心思想 | 典型应用 | 优点 | 缺点 |
|------|------|----------|----------|------|------|
| **数据流** | 批处理 | 整批→下一步，不交互 | 月末结算、工资发放、日志离线处理 | 简单、吞吐量高 | 不交互、延迟大 |
| | 管道-过滤器 | 流式、独立小过滤、松耦合 | Unix Shell、编译器、ETL、日志流 | 松耦合、易复用、可组合 | 不适合交互、传输开销 |
| **调用返回** | 主程序-子程序 | 层次化分解 | 早期结构化程序 | 简单易理解 | 耦合重 |
| | 面向对象 | 封装继承多态 | 大部分 OO 系统 | 高内聚、易扩展 | 对象间隐式依赖 |
| | 层次结构 | 每层只调用下层 | OSI、TCP/IP、OS 内核、J2EE 分层 | 易扩展、职责清晰 | 层过多性能差、层边界难划 |
| **独立组件** | 进程通信 | 独立进程间消息传递 | 微服务、IPC | 独立部署、故障隔离 | 通信开销、一致性难 |
| | 事件驱动（隐式调用） | 发布-订阅，松耦合 | GUI 事件、消息总线、React、Spring Event、Reactor | 解耦、易扩展、异步 | 执行顺序不确定、调试难 |
| **虚拟机** | 解释器 | 规则 → 解释执行 | JVM、SQL 引擎、正则引擎、脚本语言 | 灵活、业务规则可配置 | 慢、复杂 |
| | 基于规则系统 | 知识库 + 推理机 | 专家系统、风控规则引擎（Drools） | 业务规则独立、易改 | 规则冲突难排、性能差 |
| **仓库** | 数据库系统 | 中心数据 + 多访问者 | 传统 MIS、ERP、CMS | 数据一致性好 | 中心瓶颈、耦合 |
| | 超文本系统 | 网状链接、浏览 | Wiki、HTML、超媒体 | 联想式浏览 | 结构松散、导航难 |
| **其他重要** | C/S（两层/三层） | 客户端请求→服务器处理 | 传统桌面客户端、QQ、钉钉 | 交互好、瘦客户端 | 部署升级难（两层） |
| | B/S | 浏览器瘦客户端 | 所有 Web 系统 | 零部署、跨平台 | 客户端能力有限 |
| | MVC / MVP / MVVM | 职责分离：数据-视图-控制 | Web 前端、移动端、GUI | 解耦、易测试、易维护 | 复杂度上升、学习曲线 |

## 补充高频风格（虽不在 14 但常考）

| 风格 | 核心 | 典型应用 |
|------|------|----------|
| 黑板架构 | 知识源 + 黑板（共享数据）+ 控制（调度知识源） | 语音识别、信号处理、AI 推理 |
| REST | 资源 + 统一接口（GET/POST/PUT/DELETE）+ 无状态 + HATEOAS | 所有 HTTP API |
| 微服务 | 独立部署+去中心化+轻通信 | 大型互联网 |
| SOA | 面向服务 + ESB 总线 + 共享数据 | 传统企业 |
| RIA 富互联网 | 客户端富逻辑（插件/前端框架） | Flex / Silverlight / SPA 前身 |
| 分布式对象 | DCOM / CORBA / EJB | 早期企业级分布式 |
| 插件化（微内核） | 核心系统 + 插件扩展 | Eclipse、VS Code、Chrome、IDEA |

## 易混淆风格对比（★ 选择题坑点）

| 对比项 | 管道-过滤器 vs 事件驱动 |
|--------|--------------------------|
| 数据流 | 过滤器明确顺序，push 给下一个过滤器 | 发布后谁订阅谁收，顺序不确定 |
| 耦合 | 有顺序的低耦合 | 极低耦合 |
| 调试 | 链路清晰好调试 | 异步难调试 |

| 对比项 | 微服务 vs SOA |
|--------|---------------|
| 通信 | 轻量（REST/HTTP/MQ）去中心化 | ESB 中心化总线 |
| 数据 | 每服务独立 DB | 共享库常见 |
| 粒度 | 细 | 粗 |
| 部署 | 完全独立 | 常依赖 ESB |

| 对比项 | C/S 两层 vs C/S 三层 |
|--------|-----------------------|
| 拓扑 | 胖客户端 + 服务端 | 客户端 + 应用服务器 + DB |
| 业务逻辑 | 客户端 | 应用服务器 |
| 升级 | 客户端必装 | 瘦客户端（可 web） |

| 对比项 | 批处理 vs 管道-过滤器 |
|--------|------------------------|
| 单位 | 整批数据 | 每条流数据 |
| 延迟 | 大 | 低 |
| 交互 | 不支持 | 不支持 |

## 架构风格选择的答题套路（★ 案例/论文必用）

> 案例题问"请从 A、B 两种风格中选择适合 xxx 的，并说明理由"
> 论文可以用这个结构展开"分论点 1：痛点 → 候选 → 对比 → 选择"

**5 步法**：
1. 描述业务场景的需求痛点（性能/并发/修改/安全/可用）
2. 列 2-3 个候选风格
3. 对照表的优缺点逐一评估
4. 结合本项目实际约束（团队、工期、遗留系统）给出选择
5. 说明选这个风格后如何缓解它的固有缺点

**示例**：某电商从单体演进，候选 SOA vs 微服务
- SOA：ESB 中心化，适合已有企业级基础设施，但 ESB 单点、重量级
- 微服务：去中心化，适合互联网快速迭代，但运维复杂、分布式事务难
- 结论：本团队 20+ 研发、3 条业务线、月上线 30+ 次 → 微服务更适配
- 缓解：引入 Nacos + Sentinel + SkyWalking 全套治理组件，用 RocketMQ 最终一致性 + Seata AT 模式覆盖核心事务

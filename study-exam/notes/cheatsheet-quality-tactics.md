## 1. 质量属性六要素（★ 任何场景都按此展开）

```
刺激源 Source ──► 刺激 Stimulus ──► 【制品 Artifact】 ──► 响应 Response
                                │
                          环境 Environment
                                │
                         响应度量 Response Measure
```

| 要素 | 含义 | 示例 |
|------|------|------|
| ① 刺激源 | 谁触发 | 用户 / 黑客 / 内部研发 / 运维 / 硬件故障 |
| ② 刺激 | 具体事件 | 发起下单请求 / SQL 注入 / 部署新版本 / 服务器宕机 |
| ③ 制品 | 受影响的系统部分 | 订单服务 / 全系统 / 数据层 / 网关 |
| ④ 环境 | 发生时的状况 | 正常运行 / 大促峰值 / 单节点故障 / 灰度发布中 |
| ⑤ 响应 | 系统的动作 | 正常处理 / 熔断降级 / 自动切换 / 驳回请求 |
| ⑥ 响应度量 | 响应的量化指标 | P99 < 200ms / RTO < 30s / 成功率 99.9% / 拦截率 100% |

> 记忆口诀：刺源刺激制，环响应度量

## 2. 六大质量属性 + 关键战术矩阵（★ 默写级）

### 2A. 运行期 4 大属性

| 属性 | 定义 | 三大战术维度 | 关键战术（★ 背下来） |
|------|------|--------------|----------------------|
| **性能 Performance** | 响应速度 + 吞吐 | ① 资源需求（降需求）② 资源管理（提利用）③ 资源仲裁（调分配） | 缓存、异步并发、线程池隔离、算法优化、CDN、优先队列、资源调度、减少事件层数、Protobuf 代替 JSON |
| **可用性 Availability** | 正常运行时间占比（SLA） | ① 故障检测 ② 故障恢复 ③ 故障预防 | 心跳/Ping/异常监控、冗余（多副本跨 AZ）、选举（MHA/Sentinel）、重启（K8s liveness）、回滚（版本发布）、移除故障节点、熔断（Sentinel/Hystrix）、事务回滚（Seata） |
| **安全性 Security** | 抗攻击 + 保密 + 授权 + 不可抵赖 | ① 抵抗攻击 ② 检测攻击 ③ 从攻击恢复 | 认证（JWT/OAuth2）、授权（RBAC/ABAC）、加密（TLS 1.3/AES-256/脱敏）、签名（防抵赖）、审计日志、入侵检测（IDS/IPS）、隔离（DMZ/网络分段）、黑名单、WAF（XSS/SQL 注入） |
| **易用性 Usability** | 用户使用的难易度 | ① 运行时设计 ② 设计时支持 | 撤销/重做、向导、多语言、在线帮助、一致的 UI 范式、取消操作、进度条、操作预览 |

### 2B. 开发期 2 大属性

| 属性 | 定义 | 三大战术维度 | 关键战术（★ 背下来） |
|------|------|--------------|----------------------|
| **可修改性 Modifiability** | 修改的成本、风险、周期 | ① 限制修改范围（局部化）② 防止连锁反应 ③ 延迟绑定 | 高内聚低耦合、接口-实现分离、接口契约、配置化/规则化、发布-订阅解耦、抽象通用模块、微服务拆分（限界上下文） |
| **可测试性 Testability** | 通过测试发现缺陷的难易度 | ① 控制与分离 ② 记录与回放 | 接口-实现分离（依赖注入 Mock）、录像回放（流量复制）、内置监控（暴露指标）、可插拔接口、测试桩/ Mock、全链路自动化、压测平台 |

## 3. 补充：其他常考质量属性（ISO 9126 / McCall）

| 属性 | 所属标准 | 说明 |
|------|----------|------|
| 功能性 Functionality | ISO 9126 六特性 | 适合性、准确性、互操作性、保密性、合规性 |
| 可靠性 Reliability | ISO 9126 六特性 | 成熟性、容错性、易恢复性；= 可用性 + 可靠性更偏"不出错" |
| 效率 Efficiency | ISO 9126 六特性 | 时间特性（性能）、资源特性 |
| 维护性 Maintainability | ISO 9126 六特性 | 易分析、易变更、稳定、可测试 |
| 可移植性 Portability | ISO 9126 六特性 | 适应、安装、共存、易替换 |

> 注意：**可靠性 ≠ 可用性**。可靠性偏"不犯错"（MTBF、出错率），可用性偏"在线"（SLA、RTO/RPO）。

## 4. 可用性计算（★ 选择题 1 题）

```
可用性 A = MTBF / (MTBF + MTTR) × 100%
SLA 99.99% = 每年停机时间 ≤ 52.56 分钟
```

| 术语 | 全称 | 含义 | 影响 |
|------|------|------|------|
| MTBF | Mean Time Between Failures | 平均无故障时间 | 越大越好（可靠性） |
| MTTR | Mean Time To Repair | 平均修复时间 | 越小越好（恢复能力） |
| MTTF | Mean Time To Failure | 平均故障前时间 | 越大越好 |
| RTO | Recovery Time Objective | 恢复时间目标 | 业务最大容忍停机时间 |
| RPO | Recovery Point Objective | 恢复点目标 | 业务最大容忍数据丢失窗口 |

| SLA | 年度停机时间 | 月度停机时间 | 典型场景 |
|-----|-------------|-------------|----------|
| 99% | 3.65 天 | 7.2 小时 | 内部系统 |
| 99.9% | 8.76 小时 | 43.2 分钟 | 一般互联网产品 |
| 99.95% | 4.38 小时 | 21.6 分钟 | 中高端 SaaS |
| **99.99%** | **52.56 分钟** | **4.32 分钟** | **核心交易/支付（架构师常用目标）** |
| 99.999% | 5.26 分钟 | 25.9 秒 | 电信级、银行核心 |

## 5. 案例题答题 5 步法（★ 案例第 1 题必考）

> 案例题问"请识别场景对应的质量属性，写出六要素，并给出改进战术"

**步骤**：
1. **定属性**：读题 → 定位属于性能？可用性？安全性？可修改性？（有时是多个）
2. **套六要素**：从原文中提炼 6 要素
3. **选战术**：从上面矩阵中选 3-5 个匹配的战术
4. **对号入座**：把战术分别放入矩阵维度
5. **写出权衡**：说明方案的副作用和缓解措施

**示例（2024 年真题）**：
题目场景：双 11 大促期间，某电商订单系统峰值 8 万 TPS，用户反馈点提交卡顿，P99 从 150ms 涨到 1.8s，部分用户重复提交导致订单重复。

| 六要素 | 对应内容 |
|--------|----------|
| 刺激源 | 正常用户（大促秒杀流量） |
| 刺激 | 8 万 TPS 下单请求 + 重复提交 |
| 制品 | 订单服务 + 交易链路 |
| 环境 | 双 11 大促峰值 2 小时窗口 |
| 响应 | 服务排队、响应慢、重复下单 |
| 响应度量 | P99 150ms → 1800ms、订单重复率 0.5% |

| 属性 | 原因分析 | 改进战术 |
|------|----------|----------|
| 性能差 | 数据库热锁 + 线程池满 | ① 资源管理：多级缓存（Caffeine + Redis）+ RocketMQ 异步削峰 ② 资源需求：数据库索引优化 + 热点行更新拆分 ③ 资源仲裁：下单请求优先级队列 |
| 数据一致性差（功能+安全） | 重复提交没防重 | ① 前端按钮置灰 + 防重点击 ② 后端 Token 幂等 + 订单号唯一索引 ③ 响应返回后异步解耦非核心流程 |

## 6. 论文通用质量属性论据结构（论文可直接用）

```
本项目重点保障的质量属性按优先级为：可用性 > 性能 > 安全性 > 可修改性 > 可测试性。
（1）可用性方面，采用"三副本跨 AZ + K8s 自动重启 + Sentinel 熔断降级 + 全链路监控告警"的组合战术，RTO 控制在 30 秒内，RPO 为 0，年 SLA 达 99.99%。
（2）性能方面，实施"多级缓存 + 异步消息削峰 + 分库分表"的三层优化，核心接口 P99 响应 < 150ms，峰值 QPS 扛住 8 万。
（3）安全性方面，落实"JWT 鉴权 + TLS 传输加密 + AES 落盘 + WAF 拦截 + 审计日志不可篡改"的纵深防御。
（4）可修改性方面，遵循 DDD 限界上下文拆分，服务间松耦合，典型需求上线周期 < 1 周。
（5）可测试性方面，全链路单测覆盖率 70% + 自动化回归 80% + 全链路压测平台。
```

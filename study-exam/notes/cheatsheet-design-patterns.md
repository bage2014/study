## 1. 设计模式三大类别 + 23 种总表

### 1.1 创建型（5 种）：**怎么造对象**

| 序号 | 模式 | 一句话解释 | 典型应用 | 记忆 |
|------|------|------------|----------|------|
| 1 | 单例 Singleton | 全局一个实例 | 配置对象、线程池、连接池、Spring Bean 默认 | "独生子" |
| 2 | 工厂方法 Factory Method | 每个产品一个工厂子类（抽象工厂的一对一版） | 日志（File/DB/Kafka 日志各有对应工厂） | "专厂造专品" |
| 3 | 抽象工厂 Abstract Factory | 一个工厂造一族产品（多产品族） | UI 跨平台：Windows 一族 / Mac 一族，每族有 Button + TextBox + Dialog | "整族打包" |
| 4 | 建造者 Builder | 分步构建复杂对象 | StringBuilder、MyBatis XML 配置、SQL 构造器、Lombok @Builder | "一步一步搭积木" |
| 5 | 原型 Prototype | 克隆已有对象代替 new | Spring Bean scope=prototype、深拷贝场景、创建成本高时克隆 | "复制粘贴" |

### 1.2 结构型（7 种）：**类/对象怎么组合**

| 序号 | 模式 | 一句话解释 | 典型应用 | 记忆 |
|------|------|------------|----------|------|
| 6 | 适配器 Adapter | 把一个接口转成客户需要的接口（兼容） | 读卡器（SD 卡→USB）、JDBC-ODBC Bridge、Spring HandlerAdapter | "转接头" |
| 7 | 桥接 Bridge | 抽象与实现分离，各自独立变化（继承转组合） | 跨平台图形库（Window/Icon 抽象 + X11/Mac/Windows 实现）、JDBC 设计 | "各走各路" |
| 8 | 组合 Composite | 部分-整体树状结构，单个与组合一致 | 文件目录（文件 + 文件夹）、XML DOM、菜单子菜单、HR 组织树 | "树" |
| 9 | 装饰 Decorator | 不修改原类，动态加功能（透明组合） | Java IO（FileInputStream → BufferedInputStream → DataInputStream）、Spring AOP 装饰代理 | "套娃加buff" |
| 10 | 外观 Facade | 对外提供统一高层接口，封装子系统复杂性 | 医院前台（挂号/问诊/缴费一层包办）、Controller 层（封装 Service）、第三方 SDK 的 Wrapper | "前台小姐姐" |
| 11 | 享元 Flyweight | 共享细粒度对象，减少内存 | 字符串常量池、Integer 缓存池、棋盘上的格子（内蕴状态共享，外蕴状态区分） | "共享经济" |
| 12 | 代理 Proxy | 代理对象控制对真实对象的访问 | 静态代理、JDK 动态代理（Spring AOP）、CGLib、RPC 客户端代理、虚拟代理（懒加载图片）、保护代理（权限） | "代跑腿" |

### 1.3 行为型（11 种）：**对象之间怎么协作**

| 序号 | 模式 | 一句话解释 | 典型应用 | 记忆 |
|------|------|------------|----------|------|
| 13 | 责任链 Chain of Responsibility | 请求在链上依次传，谁能处理谁上 | Servlet Filter、Spring Interceptor、Tomcat Pipeline、OKHttp 拦截器、支付风控链 | "击鼓传花" |
| 14 | 命令 Command | 请求封装为对象（命令对象），支持 undo/redo/排队 | 菜单项（Menu Item → Action）、线程池 Runnable、事务命令、操作系统进程 | "按遥控器" |
| 15 | 解释器 Interpreter | 定义文法 + 解释器执行 | SQL 解析器、正则引擎、表达式（如 SpEL、OGNL）、规则引擎部分实现 | "翻译官" |
| 16 | 迭代器 Iterator | 顺序访问集合元素，不暴露内部结构 | Java Collection Iterator、增强 for 循环、Cursor | "遍历不踩坑" |
| 17 | 中介者 Mediator | 用中介对象封装一组对象交互，解耦网状依赖 | MVC 中的 Controller（M-V 中介）、聊天服务器、航班塔台、消息总线简化版 | "居委会大妈" |
| 18 | 备忘录 Memento | 不破坏封装地保存/恢复对象状态 | Ctrl+Z、游戏存档、数据库 Savepoint、快照 | "后悔药" |
| 19 | 观察者 Observer | 一对多依赖，变化广播通知订阅者 | JavaFX/JS 事件、Spring ApplicationEvent、消息发布订阅、Vue 响应式、RxJava | "广播" |
| 20 | 状态 State | 状态改变时改变行为，类代替 if-else/switch | 订单状态流转（待付款→已付款→已发货→完成/取消）、电梯状态、TCP 连接状态 | "变身" |
| 21 | 策略 Strategy | 封装不同算法，可互换，类代替 if-else | Collections.sort() 自定义 Comparator、支付方式选择（微信/支付宝/银联）、打折促销多种策略 | "锦囊妙计" |
| 22 | 模板方法 Template Method | 父类定骨架，子类重写具体步骤 | HttpServlet（doGet/doPost 钩子）、Spring JdbcTemplate/RestTemplate、造房子（打地基/砌墙/封顶） | "骨架你来填肉" |
| 23 | 访问者 Visitor | 稳定数据结构 + 易变操作分离，在不修改元素的前提下加新操作 | 编译器语义分析、报表生成（对同一数据出多种格式：PDF/Excel/HTML）、AST 遍历 | "上门服务" |

## 2. 记忆口诀（助记分类）

```
创建型 5： 单抽原建工   （单例、抽象工厂、原型、建造者、工厂方法）
结构型 7： 适桥装代组享外（适配器、桥接、装饰、代理、组合、享元、外观）
行为型 11：责命解迭中备观，状策模访解   （责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者）
```

> 口诀不顺的话，记住另一个更流行的：
> - 创建：**简（建）单（单）原抽工**（建-单-原-抽-工）
> - 结构：**组（组）装（装）配（配）带（代）桥（桥）适（适）享（享）**（6+1）
> - 不对，死背分类性价比最高的方式是：**每天早晨写一遍分类**

## 3. 易混淆模式对比（选择/案例坑点）

| 对比 | 区别 |
|------|------|
| **工厂方法 vs 抽象工厂** | 工厂方法：1 个产品等级（一条产品线）。抽象工厂：多个产品族（多条相关产品线一起造）。 |
| **代理 vs 装饰** | 代理：控制访问（权限/懒加载/缓存），核心相同功能。装饰：增强功能，层层叠加上去。 |
| **适配器 vs 外观** | 适配器：改接口兼容（老接口→新接口），对象数 1:1。外观：统一高层接口，封装 n 个子系统。 |
| **策略 vs 状态** | 策略：客户主动切换算法（外部控制）。状态：对象内部状态变化自动切换行为（内部控制）。 |
| **观察者 vs 中介者** | 观察者：一对多广播，无中心。中介者：多对多经中心转发，有中心。 |
| **组合 vs 装饰** | 组合：部分-整体树，重点是"层级"。装饰：透明增强，重点是"加功能"。 |
| **命令 vs 策略** | 命令：封装"请求/动作"（do/undo）。策略：封装"算法"（同接口不同实现）。 |

## 4. 案例题高频考法

### 4.1 考法 1：给出场景 → 选合适模式（1-3 分）
- "电商系统需要多种支付方式（微信/支付宝/银联），后期还要扩展 ApplePay、PayPal，最适合的模式是？" → **策略模式**
- "报表系统需要对同一份订单数据生成 PDF / Excel / HTML / CSV 四种格式，数据结构稳定，格式频繁扩展" → **访问者模式**
- "订单状态流转复杂（创建/支付/发货/签收/取消/退款），if-else 过多难维护" → **状态模式**
- "日志系统支持多种输出（File/DB/MQ/Kafka），且不同组合可以叠加（同步+异步+缓冲+加密）" → **装饰模式**

### 4.2 考法 2：补类图（5-8 分）
要求熟悉 **5 种核心模式的 UML 类图要素**（必须会手画/会补）：
1. **观察者**：Subject（attach/detach/notify）+ Observer（update），ConcreteSubject / ConcreteObserver
2. **策略**：Context（持有 Strategy 引用）+ Strategy（算法接口）+ ConcreteStrategyA/B
3. **工厂方法**：Product + ConcreteProduct + Creator（工厂方法 createProduct）+ ConcreteCreator
4. **代理**：Subject + RealSubject + Proxy（持有 RealSubject）
5. **装饰**：Component + ConcreteComponent + Decorator（持有 Component 引用）+ ConcreteDecoratorA/B

### 4.3 考法 3：写出某模式的优缺点 / 适用场景
- 单例优点：节约资源、全局统一；缺点：难测试、扩展性差
- 观察者优点：解耦、广播通知；缺点：通知顺序不可控、循环引用
- 访问者优点：新增操作容易、集中相关操作；缺点：加新元素难（违反开闭）、破坏封装

## 5. 架构师论文中的模式使用（加分点缀）

> 论文中不必写太多模式，写出 2-3 个与项目契合的即可，关键是"切题"。

**示例片段**（微服务/网关场景）：
```
在 API 网关组件的设计中，为支持"鉴权、限流、日志、监控"等多个横切能力可插拔扩展，我们采用了【责任链模式】：每条请求经过认证过滤器 → 权限过滤器 → 限流过滤器 → 日志过滤器 → 路由过滤器 形成的调用链，每个过滤器独立实现且支持热插拔。同时，对于灰度发布场景，我们引入【策略模式】封装了"按百分比流量 / 按用户标签 / 按 Header 规则"三种灰度路由策略，业务方可根据需求动态切换策略，无需改网关代码。
```

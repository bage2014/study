#### 试题一（上半年）：论大数据的 Lambda 架构

【说明】
大数据场景下，系统既要处理海量历史数据的批量分析，又要处理实时流入的流数据以支撑毫秒级决策。Lambda 架构由 Nathan Marz 提出，通过"批处理层 + 实时处理层 + 服务层"三层并行的方式，兼顾数据的准确性与实时性，是早期大数据系统的经典参考架构。它以不可变的事实事件为输入，批层用 Hadoop/Spark 离线计算全量视图，速层用 Storm/Spark Streaming 处理增量视图，服务层合并两类视图对外查询。

【要求】请围绕"大数据的 Lambda 架构"论题，依次从以下三个方面进行论述：
1. 概要叙述你参与管理和开发的软件项目以及你在其中所担任的主要工作。

3. 结合你具体参与的项目，说明 Lambda 架构的应用、关键挑战及应对措施。

#### 试题二（上半年）：论云原生 DevOps 与云上运维（云上自动化运维）

【说明】
随着企业全面上云，传统人工运维难以应对大规模、高动态的云上环境。云原生 DevOps 以容器、微服务、不可变基础设施、声明式 API 为基石，将开发与运维通过自动化流水线深度协同，实现持续集成/持续交付（CI/CD）、基础设施即代码（IaC）、可观测性、弹性自愈与混沌工程，是云时代提升交付效率与运行稳定性的核心实践。

#### 试题三（上半年）：论单元测试

【说明】
单元测试是软件测试金字塔的底层，针对程序最小可测单元（函数/类/模块）进行独立验证，是保证代码质量、支持安全重构、驱动良好设计的基础实践。测试驱动开发（TDD）进一步将测试前置于编码之前，以"红-绿-重构"循环驱动代码演进。良好的单元测试应具备快速、独立、可重复、自验证、及时（FIRST 原则）等特征。

#### 试题四（上半年）：论模型驱动架构设计方法（MDA）

【说明】
模型驱动架构（MDA，Model-Driven Architecture）是 OMG 提出的以模型为核心的软件设计方法，通过计算无关模型（CIM）、平台无关模型（PIM）、平台特定模型（PSM）三层模型及其映射变换，实现业务逻辑与平台技术分离，提升模型复用与跨平台可移植性。MDA 强调以 UML 等形式化建模语言描述系统，通过变换规则自动生成代码，是模型工程与低代码的理论基础。

3. 结合你具体参与的项目，说明 MDA 的应用、关键挑战及应对措施。

#### 试题一（下半年）：论面向服务的架构设计（SOA）

【说明】
面向服务的架构（SOA，Service-Oriented Architecture）是一种将应用程序功能分解为可复用、松耦合、通过标准接口契约通信的服务集合的架构模式。SOA 强调服务的粗粒度、可重用、可编排，通常以企业服务总线（ESB）作为通信与编排中介，通过 Web Service（SOAP/WSDL）或 REST 实现互操作，是企业应用集成与业务流程编排的经典范式，也是微服务架构的理论前身。

#### 试题四（下半年）：论分布式事务及其解决方案

【说明】
在微服务与分库分表架构下，一个业务操作需跨多个独立数据库或服务完成，传统单机 ACID 事务不再适用。分布式事务需在一致性、可用性、性能之间权衡，常见方案包括 2PC/XA、TCC、Saga（补偿）、本地消息表 + 可靠消息最终一致、Seata AT 等。合理选择分布式事务方案是保障数据一致性与系统性能的关键架构决策。

## 参考范文要点（每题 3 个核心分论点 + 量化指标）

### 上半年 试题一范文要点（Lambda 架构）
1. 三层并行：批层用 Spark 批处理历史全量数据算出 Batch View，速层用 Flink 处理实时增量流算 Realtime View，服务层合并两类视图响应查询。
2. 不可变事实与重算：所有事件以不可变日志（Kafka）持久存储，批层可随时重算修正历史，速层只处理增量，保证最终准确。
3. 挑战与应对：批速双代码维护成本高（向 Kappa 演进只保留流层）；速层结果不精确用批层覆盖修正；延迟高用提速层缓存热视图。
量化：批层日处理 5TB、速层延迟 <10s、服务层查询 P95 <1s、历史可重算。

### 上半年 试题二范文要点（云原生 DevOps）
1. 容器化与 IaC：应用容器化（Docker）+ Helm 编排，基础设施用 Terraform 声明式管理，环境一键复现。
2. CI/CD 与 GitOps：GitLab CI 流水线（构建-测试-安全扫描-镜像发布），ArgoCD GitOps 自动同步集群状态，灰度发布自动化。
3. 可观测性与自愈：Prometheus 指标 + Loki 日志 + Jaeger 链路追踪三位一体；K8s HPA 自动扩缩容 + 探针自愈重启。
量化：发布频率从周级到日级、流水线自动化 100%、MTTR <15min、扩缩容响应 <3min。

### 上半年 试题三范文要点（单元测试）
1. 测试规范与覆盖：遵循 FIRST 原则与 AAA 模式，JUnit5 + Mockito 编写，覆盖核心业务逻辑，分支覆盖率门槛 80%。
2. 测试替身与隔离：用 Mockito Mock 外部依赖（DB/RPC），用 Stub 构造预期返回，保证单测独立可重复不依赖环境。
3. 挑战与应对：遗留代码难测用依赖注入解耦；测试维护成本高用表驱动测试 + 共享工厂；TDD 推广阻力用红绿重构循环培训。
量化：分支覆盖率 80%、单测执行 <30s、测试替身隔离 100% 依赖、缺陷逃逸率降 40%。

### 上半年 试题四范文要点（MDA）
1. 三层模型与变换：CIM 描述业务（用例/领域），PIM 平台无关（UML 类/状态图），PSM 平台特定（映射到 Java/.NET）；通过变换规则自动生成 PSM 与代码骨架。
2. 业务与技术分离：PIM 不绑定技术平台，换平台只改 PSM 变换规则，PIM 复用，提升可移植性与模型资产沉淀。
3. 挑战与应对：建模工具学习曲线陡用培训 + 模板；变换规则难维护用标准化的 QVT 变换语言；生成代码不够灵活用手写扩展点补充。
量化：3 层模型、模型复用率 50%、跨平台生成 2 套、开发效率提升 30%。

### 下半年 试题一范文要点（SOA）
1. 服务识别与契约：按业务能力识别粗粒度服务，用 WSDL/接口契约定义输入输出，服务注册到注册中心供发现。
2. ESB 编排与集成：ESB 承担路由、协议转换、消息中介、流程编排（BPEL），连接 ERP/CRM/OA 等异构系统松耦合。
3. 挑战与应对：ESB 易成性能瓶颈与单点（演进为去中心化微服务+网关）；服务粒度难定用领域驱动划定边界；契约兼容用版本化与向后兼容策略。
量化：识别 15 个服务、ESB 日路由 200 万次、集成 6 套系统、新业务上线周期降 40%。

### 下半年 试题二范文要点（软件维护）
1. 维护分类与流程：建立纠错/适应/完善/预防四类工单分类，变更走影响分析→评审→实施→回归测试→灰度发布流程。
2. 配置与回归：Git 分支策略 + 语义化版本管理，自动化回归测试覆盖核心用例，发布前门禁阻断回归失败。
3. 可维护性提升：模块化拆分 + 接口文档化，可观测性（指标/日志/追踪），预防性重构技术债每迭代预留 20%。
量化：维护成本占比 65%→55%、自动化回归 70%、MTTR <2h、技术债密度降 30%。

### 下半年 试题三范文要点（多源异构数据集成）
1. 集成方式选型：实时用 CDC（Canal）+Kafka 入湖，离线用 ETL（DataX）T+1 入仓，即席用 Trino 联邦查询，主数据用 MDM 统一维度。
2. 元数据与治理：统一元数据中心管理血缘/Schema 演进/质量规则，数据质量监控告警。
3. 挑战与应对：异构格式用 Avro/Parquet+字段映射；语义不一致用主数据治理统一编码；CDC 乱序用幂等+版本号；联邦性能差降级宽表。
量化：集成 8 类源、CDC 延迟 <10s、ETL 日均 500GB、联邦 P95 <8s、质量合格率 99.5%。

### 下半年 试题四范文要点（分布式事务）
1. 方案选型与权衡：强一致金融核心用 TCC（Try/Confirm/Cancel 资源预留）；高并发订单用本地消息表+RocketMQ 事务消息最终一致；长流程用 Saga 补偿；2PC/XA 因性能差不用于高并发。
2. CAP/BASE 理论落地：分区容错必选，权衡 CP 与 AP，互联网选 AP+最终一致（BASE：基本可用/软状态/最终一致），通过幂等+对账+补偿兜底。
3. 挑战与应对：TCC 改造量大用 Seata TCC 框架降成本；消息可靠投递用本地消息表+重试+幂等消费；空回滚/悬挂用防悬挂事务控制表；对账兜底每日 T+1 差错修复。
量化：订单链路 4 服务、事务消息延迟 <1s、幂等消费 100%、对账差错率 <0.01%、TCC 改造 8 个接口。

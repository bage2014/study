# 2022 年 系统架构设计师 下午案例分析 真题

> 考试时间：90 分钟 | 题量：5 道大题（必答） | 满分 75 分 | 合格 45 分
> 来源：网络公开真题汇编（考生回忆版 + 公开解析）
> 注意：第 1 题通常为质量属性识别；第 3 题通常为嵌入式

## 试题一（15 分）：质量属性 + 架构风格

【说明】
某商业银行拟重构核心账务系统，支持存款、贷款、结算、对账等业务。日均交易 2000 万笔，月末批量结息高峰 5 亿笔。需求描述如下：

a. 核心账务数据零丢失，单笔交易原子性提交，故障后可通过日志完整恢复。
b. 联机交易响应时间不超过 200ms，日间峰值 TPS 不低于 1 万。
c. 支持新增理财产品类型、新计息规则，2 人周内完成开发上线。
d. 对客户敏感信息（身份证、余额）全链路加密，操作行为可审计。
e. 月末批量结息在 4 小时窗口内完成 5 亿笔结息。
f. 系统双活部署，RPO=0，RTO 不超过 3 分钟。
g. 提供灰度发布能力，新功能可按分行逐步放量。
h. 柜员操作界面与原系统保持一致，培训 0.5 天即可上手。

架构师提出方案一采用批处理风格（联机与批量分离），方案二采用事件驱动风格（以事件总线为核心，账务变动产生领域事件驱动下游）。

【问题 1】（8 分）
将上述 a-h 需求对应的质量属性填入下表并各给一条理由。

| 需求 | 质量属性 | 识别理由 |
|------|----------|----------|
| a | （1）________ | 零丢失、可恢复 |
| b | （2）________ | 响应时间、TPS |
| c | （3）________ | 新增功能工作量 |
| d | （4）________ | 加密、审计 |
| e | （5）________ | 批量吞吐 |
| f | （6）________ | 双活、RPO/RTO |
| g | （7）________ | 灰度逐步放量 |
| h | （8）________ | 界面一致、培训成本 |

【问题 2】（4 分）
从交互方式、数据结构、控制结构、扩展方法对比批处理风格与事件驱动风格。

【问题 3】（3 分）
针对"月末批量结息"与"联机实时账务"并存的场景，应如何结合两种风格？说明理由。

【参考答案】

【问题 1】
| 需求 | 质量属性 | 识别理由 |
|------|----------|----------|
| a | （1）可靠性/安全性 | 零丢失、可恢复属于可靠性 |
| b | （2）性能 | 响应时间、TPS 属于性能 |
| c | （3）可修改性 | 新增功能工作量 |
| d | （4）安全性 | 加密、审计保护机密性 |
| e | （5）性能 | 批量吞吐量指标 |
| f | （6）可用性 | 双活、RPO/RTO 故障恢复 |
| g | （7）可修改性/可运维性 | 灰度放量 |
| h | （8）易用性 | 界面一致降低培训成本 |

【问题 2】
| 对比维度 | 批处理风格 | 事件驱动风格 |
|----------|-----------|-------------|
| 交互方式 | 顺序提交作业，批量执行 | 发布/订阅，松耦合异步交互 |
| 数据结构 | 文件/批量数据集 | 事件消息（不可变事实） |
| 控制结构 | 作业调度器驱动，显式触发 | 事件触发，隐式调用 |
| 扩展方法 | 新增作业步骤 | 新增事件订阅者，不影响发布方 |

【问题 3】
结合方案：联机实时账务采用事件驱动风格（账务变动产生领域事件，实时驱动账务明细、风控、通知等下游）；月末结息采用批处理风格（调度器在窗口期批量扫描账户、计算利息、批量提交）。理由：联机交易要求低延迟、松耦合扩展，事件驱动适合；结息是海量数据集中处理的作业型任务，批处理吞吐高、事务边界清晰。两者通过共享账务数据库 + 事件总线衔接。

## 试题二（15 分）：UML 建模 / 设计模式

【说明】
银行核心系统需要统一的支付路由：根据金额、渠道（柜面/手机/网银）、币种、风控等级选择不同的支付通道（大小额、超级网银、第三方）。路由规则频繁变化。

【问题 1】（6 分）
用 UML 类图描述支付路由采用策略模式的结构。

【问题 2】（5 分）
说明观察者模式在"支付结果通知"中的应用（通知短信、微信、柜员回显等多渠道）。

【问题 3】（4 分）
说明开闭原则与依赖倒置原则，并指出策略模式如何体现。

【参考答案】

【问题 1】
- PaymentContext（支付上下文）：持有 RoutingStrategy 引用，route(Payment) 委托策略。
- RoutingStrategy（抽象策略）：route(Payment) → Channel。
- BigAmountStrategy（大额走大小额）、CrossBankStrategy（跨行走超级网银）、ThirdPartyStrategy（小额走第三方）。
关系：PaymentContext 聚合 RoutingStrategy，运行时注入；新增通道只新增策略类。

【问题 2】
观察者模式应用：Subject = PaymentResultNotifier（支付结果主题），维护观察者列表。Observer 接口 = notify(PaymentResult)。具体观察者：SmsNotifier、WechatNotifier、TellerDisplayNotifier。支付完成后主题 notify，各观察者各自实现通知逻辑，互不影响，新增通知渠道只需新增观察者。

【问题 3】
开闭原则：对扩展开放，对修改关闭——扩展功能时新增类而非改老代码。
依赖倒置：高层模块不依赖低层模块，二者都依赖抽象。
策略模式体现：PaymentContext（高层）依赖 RoutingStrategy 抽象接口，不依赖具体策略类（低层）；新增策略只新增实现类，不改 Context，符合开闭原则。

## 试题三（15 分）：嵌入式系统

【说明】
某车载 T-Box 基于 AUTOSAR 架构，需对接 4G 模组、CAN 总线、GNSS 定位。远程查询车辆位置时，应用层 SWC 通过 RTE 调用底层通信服务获取 GPS 数据。

【问题 1】（5 分）
说明 AUTOSAR 分层结构（自下而上）及 RTE 的作用。

【问题 2】（5 分）
说明 CAN 总线通信中，应用层 SWC 如何通过 RTE 与 BSW 通信服务交互获取总线数据。

【问题 3】（5 分）
说明车载软件 OTA 升级失败自动回滚的 A/B 分区原理。

【参考答案】

【问题 1】
AUTOSAR 自下而上：微控制器层（MCAL：片内外设驱动）→ ECU 抽象层（统一 I/O 抽象）→ 基础软件服务层 BSW（OS、通信、诊断、内存管理）→ 运行环境 RTE → 应用层 ASW（软件组件 SWC）。
RTE 作用：应用层与 BSW 之间的抽象通信中间件，为 SWC 提供统一通信服务（信号/服务），屏蔽底层硬件与总线差异，实现应用软件硬件无关性与可移植性。

【问题 2】
SWC 不直接访问 CAN 驱动。流程：SWC 通过端口（Port）向 RTE 发起数据请求/被 RTE 周期触发 → RTE 调用 BSW 通信服务（Com 模块）→ Com 调用 PduR（PDU 路由）→ CAN 接口层（CanIf/CanDrv）读取总线帧 → 数据经 COM 层解析为信号沿原路经 RTE 回送到 SWC 端口变量。SWC 全程只与 RTE 交互，不感知 CAN 协议细节。

【问题 3】
A/B 分区原理：存储划分 Slot A（当前运行）和 Slot B（备用）两个独立分区。
1. 新固件下载写入当前未运行分区（如 Slot B），校验 CRC/SHA。
2. 切换 Bootloader 启动优先级为 Slot B，重启。
3. 新版本启动后限时内完成健康自检并写"成功"标记。
4. 若启动失败/超时未写标记，Bootloader 下次启动自动回退到 Slot A 上个稳定版本。
优势：任何时刻都有一个可用固件，升级失败不变砖。

## 试题四（15 分）：数据库设计

【说明】
某银行交易流水表 trade_detail 日新增 3000 万条，3 年累计约 30 亿条。查询场景：① 按账户+日期查明细（60%）；② 按日期范围做对账汇总（30%）；③ 按商户统计月度交易额（10%）。

【问题 1】（6 分）
说明该表分库分表策略与全局 ID 方案。

【问题 2】（5 分）
说明将冷数据（1 年前）迁移到列式存储的优势。

【问题 3】（4 分）
说明数据库三级模式与两级映象的作用。

【参考答案】

【问题 1】
分库分表策略：按 account_id 哈希分库（数据均匀、按账户查询可定位单库），按 trade_date 范围分表（按月一张表，便于按日期查询裁剪与冷热分离）。全局 ID：采用雪花算法 Snowflake（时间戳+机器 ID+序列号），保证全局唯一、趋势递减写入。

【问题 2】
列式存储（如 ClickHouse）优势：
1. 列存只读查询所需列，I/O 减少 10-50 倍。
2. 向量化 SIMD 执行，聚合速度百倍提升。
3. 同列数据同质压缩比高（5-10:1）。
4. 支持 MergeTree 预聚合引擎，对账汇总秒级返回。

【问题 3】
三级模式：外模式（用户视图）、概念模式（全局逻辑）、内模式（物理存储）。
两级映象：外模式/概念模式映象保证逻辑数据独立性（概念模式变不影响外模式）；概念模式/内模式映象保证物理独立性（存储变不影响逻辑模式）。

## 试题五（15 分）：Web 系统架构 / 湖仓一体

【说明】
该银行建设数据中台，将原数据仓库（离线 T+1 批处理）演进为湖仓一体架构，支持实时风控、实时报表、历史回溯。数据源包括 MySQL Binlog、Kafka 实时流、文件日志。

【问题 1】（5 分）
说明湖仓一体相对"数据湖+数据仓库"分离架构的优势（至少 4 点）。

【问题 2】（5 分）
说明 Lambda 架构与 Kappa 架构的区别，及湖仓一体如何融合。

【问题 3】（5 分）
说明 Flink + Iceberg/Hudi 实现湖仓一体的核心机制（至少 3 点）。

【参考答案】

【问题 1】
湖仓一体优势：
1. 统一存储：一份数据同时支持批与流，避免数据湖与数仓双份存储与不一致。
2. 事务支持：表级 ACID，支持 upsert/delete，解决湖不可改难题。
3. 模式管理：统一元数据与 Schema 演进，支持血缘与时间旅行。
4. 多引擎共享：Spark/Flink/Trino/机器学习引擎共享同一数据，无需搬运。
5. 成本：开放存储格式（Parquet）+ 对象存储，成本低于专有数仓。

【问题 2】
Lambda：批层（Hadoop 离线）+ 速层（流处理实时）+ 服务层合并，架构复杂需维护两套代码。
Kappa：只保留流层，以 Kafka 为单一真相源，重算即重放流，架构简化但历史回溯受限于 Kafka 保留。
湖仓一体融合：以开放表格式（Iceberg/Hudi）为统一存储，Flink 流式写入既可实时查询又可批量回溯，不再区分批速层，兼具 Lambda 全场景与 Kappa 简化。

【问题 3】
Flink + Iceberg/Hudi 核心机制：
1. 流式写入：Flink CDC 实时消费 Binlog/Kafka，以 upsert 方式写入湖表，支持行级 ACID 与主键合并。
2. 时间旅行：表格式保留多快照，支持按时间戳回溯任意历史版本，满足回溯审计。
3. Schema 演进：支持增删改列而不重写全表，配合元数据中心管理血缘。
4. 分区与谓词下推：查询引擎下推分区过滤到存储层，按分区裁剪，实时与批量查询共享同一物理数据。

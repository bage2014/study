# 第一部分　2026 年上半年（5 月 23 日）

## 试题一（25 分）：质量属性 + 架构风格（入侵检测与告警系统）

【说明】某园区计划构建智能化的入侵检测与告警系统，全面覆盖办公区、仓储区及核心机房等关键防护区域。平台需 7×24 不间断运行，持续汇聚并处理来自门禁控制、视频监控、周界防护及系统日志等多源异构数据，针对各类异常行为执行实时检测、深度剖析与预警，并将研判结论及时分发给安保与运维团队。核心需求如下：

a. 当系统出现局部组件失效时，核心告警功能必须保持可用，不受波及。
b. 在业务流量峰值期间，系统需具备高吞吐量，确保大规模实时事件流得到持续处理，并以极低延迟完成研判与告警。
c. 平台需具备协议可扩展性，接入新类型传感器协议时，应将对既有业务模块的代码侵入和改动降至最低。
d. 系统常态运行时，若发生未授权的越权访问行为，必须在 1 秒内触发告警，并将其详细轨迹留存至安全审计日志。
e. 主分析节点发生宕机等故障时，系统应具备自动容灾切换能力，平滑迁移至备用节点，确保业务连续性不中断。
f. 安全管理员需具备对异常访问链路的溯源能力，系统须确保审计记录的完整性与防篡改性。
g. 系统应支持检测规则的灵活扩展，新增检测规则时应以插件化或扩展方式融入，避免干扰或修改现有处理链路。
h. 针对高危级别的入侵事件，系统必须在规定的时间约束内完成精准识别，并确保告警结果成功推送。

在数据处理机制上，平台需针对持续涌入的海量数据，构建流水线处理模式，按序执行数据采集、协议解析、格式标准化、特征提取、规则匹配及告警输出等串联环节。架构师需在**管道-过滤器**与**批处理**两种风格中选型，并完成构件设计。

【问题 1】（12 分）请指出需求 a~h 分别对应的质量属性。

| 需求 | 质量属性 | 需求 | 质量属性 |
|------|----------|------|----------|
| a | （1）可用性 | e | （5）可用性 |
| b | （2）性能 | f | （6）安全性（完整性） |
| c | （3）可修改性 | g | （7）可修改性 |
| d | （4）安全性 | h | （8）性能 |

**参考答案**：(1)可用性 (2)性能 (3)可修改性 (4)安全性 (5)可用性 (6)安全性（完整性） (7)可修改性 (8)性能。
陷阱：f 中"完整性与防篡改"→安全性；a 与 e 都是可用性但侧重不同（a=故障隔离、e=故障转移）。

【问题 2】（6 分）从交互方式、数据结构、控制结构、扩展方法四方面比较管道-过滤器与批处理风格，并说明本题应选哪种。

| 对比维度 | 管道-过滤器 | 批处理 |
|----------|------------|--------|
| 交互方式 | 过滤器间通过管道**流式**传递，边产生边处理 | 阶段间传递**完整数据**，整批串行 |
| 数据结构 | 数据流（逐段/增量） | 完整数据集 |
| 控制结构 | 数据到达即驱动下一过滤器（数据流驱动） | 上一阶段全部完成才进入下一阶段 |
| 扩展方法 | 新增/替换过滤器，可并行 | 新增处理阶段 |

**选型**：选**管道-过滤器**。理由：本题为持续涌入的实时事件流，要求低延迟（需求 b/h），需边采集边解析边匹配；批处理需等整批完成，无法满足实时性，且接入新协议/新规则时（需求 c/g）过滤器可独立替换，侵入更低。

【问题 3】（7 分）请为本系统设计构件组成（至少 4 类构件），并说明各构件职责。

**参考答案**（典型构件设计）：
1. **数据采集构件（适配器）**：对接门禁/视频/周界/日志等异构数据源，屏蔽协议差异，对应需求 c 的协议可扩展——新协议只需新增适配器。
2. **协议解析与标准化构件**：将异构数据解析为统一内部格式（数据清洗/格式标准化）。
3. **特征提取构件**：从标准化数据中提取检测所需特征。
4. **规则匹配构件（插件化）**：加载检测规则执行匹配，规则以插件形式扩展，对应需求 g——新增规则不改主链路。
5. **告警输出构件**：将研判结论分发给安保与运维团队。
6. **共享数据仓储/黑板**（可选）：保存当前态势与中间结果，支持多知识源协同。
每个构件间通过管道连接，故障隔离（需求 a）通过构件冗余/降级实现。

## 试题二（25 分）：IoT + 时序数据库 + MQTT（智慧养老家居系统）

【说明】某公司开发智慧养老家居系统，通过各类传感器（心率、跌倒、门磁、烟感等）采集老人居家数据，经网关汇聚后上传云端，供家属、社区与医护人员查看与预警。需在众多 IoT 技术栈中选型，并解决高频时序数据的存储与实时告警问题。

【问题 1】（8 分）请为该系统选配 IoT 技术栈（感知层/网络层/平台层/应用层），并说明各层典型技术。

**参考答案**：
- **感知层**：各类传感器（心率/跌倒/门磁/烟感）+ RFID/蓝牙 Beacon + 摄像头；低功耗 MCU。
- **网络层**：短距 Zigbee/BLE/Wi-Fi 接入网关；网关→云端用 4G/5G/NB-IoT（NB-IoT 低功耗广域，适合电池供电传感器）。
- **平台层**：IoT 平台（设备接入/注册/影子/规则引擎）+ 时序数据库（存储传感器时序数据）+ 消息中间件 MQTT Broker。
- **应用层**：家属 App/社区大屏/医护端 + 告警推送。

【问题 2】（8 分）系统每秒产生数万条传感器读数，请选择合适的数据库并说明选型理由（与关系型数据库对比）。

**参考答案**：选**时序数据库（TSDB）**，如 InfluxDB/TDengine/Prometheus。理由：
1. 数据模型为（设备 ID, 时间戳, 指标值），写入量极大且为追加写，TSDB 采用 LSM 树 + 列式存储，写入吞吐比关系型高一个数量级；
2. 自带降采样（降精度）与冷热分层（热数据 SSD / 冷数据对象存储），应对海量历史数据；
3. 内置时间维度查询与聚合函数，适合"查询某老人最近 24 小时心率趋势"类查询；
4. 关系型数据库高频追加写会产生大量页分裂与索引维护开销，且无原生降采样，成本高。

【问题 3】（9 分）MQTT 协议有三种 QoS 等级，请说明各自含义，并为下列场景选择合适的 QoS：① 老人跌倒告警（必须送达）；② 心率每秒上报（高频、允许偶尔丢失）；③ 设备状态（在线/离线）变更通知。

**参考答案**：
- **QoS 0（最多一次）**：发完即弃，不确认，可能丢失——性能最高。
- **QoS 1（至少一次）**：接收方回 PUBACK 确认，确保送达但可能重复——需消费方幂等。
- **QoS 2（恰好一次）**：四次握手（PUBLISH→PUBREC→PUBREL→PUBCOMP），确保不丢不重——开销最大。

选型：① 跌倒告警→**QoS 2**（生命安全，必须送达且不能重复误报）；② 心率高频上报→**QoS 0**（丢一两个点可接受，保吞吐降功耗）；③ 状态变更通知→**QoS 1**（确保送达，允许重复但消费端幂等处理即可）。

## 试题三（25 分）：Redis 高并发与超卖（悲观锁/乐观锁）

【说明】某电商秒杀系统使用 Redis 预扣库存，活动开始时瞬时并发极高，出现了超卖现象。架构师需对比悲观锁与乐观锁两种方案，并给出 Redis 层的优化策略。

【问题 1】（8 分）请说明悲观锁的分类及其实现方式（至少 2 种）。

**参考答案**：
- **数据库悲观锁**：`SELECT ... FOR UPDATE`（行锁），事务内锁定库存行，其他事务阻塞等待；实现简单但并发度低、易死锁。
- **Redis 分布式悲观锁**：`SET key value NX EX`（SETNX + 过期）抢锁，抢到才执行扣减，释放时用 Lua 校验 value 后 DEL 防误删；依赖 Redisson 等框架可实现可重入锁。
- 本质：先加锁再操作，"先假设会冲突"，适合写冲突概率高的场景。

【问题 2】（8 分）对比悲观锁与乐观锁，说明各自优缺点与适用场景；本秒杀场景推荐哪种，为什么？

| 维度 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 思想 | 先加锁再操作，假设会冲突 | 先操作，提交时校验冲突，假设不冲突 |
| 实现 | FOR UPDATE / 分布式锁 | 版本号/CAS（Redis Lua + WATCH） |
| 优点 | 强一致、实现简单 | 并发度高、无锁等待 |
| 缺点 | 并发度低、可能死锁、阻塞 | 冲突高时重试风暴、写放大 |
| 适用 | 写冲突概率高、临界区短 | 读多写少、冲突概率低 |

**推荐**：秒杀属写冲突极高场景，**纯乐观锁会导致大量重试（CAS 失败循环），反而劣化**；推荐 **Redis Lua 原子预扣（服务端串行化）+ 数据库兜底乐观锁**——Lua 脚本在 Redis 单线程内原子完成"判断库存→扣减→记录"，从源头避免超卖与并发竞争，数据库层用乐观锁做最终兜底。

【问题 3】（9 分）请给出至少 4 条 Redis 层的高并发优化策略。

**参考答案**：
1. **Lua 原子预扣**：将判断+扣减封装为 Lua 脚本，单线程原子执行，杜绝超卖。
2. **库存分片（分桶）**：把总库存拆成 N 个 key（如 stock_0..stock_63），请求哈希到不同桶，分散热点。
3. **本地缓存兜底**：网关/服务层用 Caffeine 做本地缓存，挡掉大部分读请求，减轻 Redis 压力。
4. **过期 key 随机化**：秒杀 key 设置 TTL 时加随机抖动，避免大批 key 同时过期引发缓存雪崩。
5. **限流降级**：入口限流（令牌桶），超过预估并发直接返回"已抢完"，保护 Redis。
6. **预热与多级缓存**：活动前将热点商品库存预热到 Redis + CDN 静态化页面。
7. **关闭持久化/主从异步**：秒杀期间可临时关闭 AOF/RDB 持久化提升写入性能（事后恢复）。

## 试题四（25 分）：AIoT 智能安防云边协同

【说明】某智能安防系统采用云边协同架构：边缘节点（摄像头/门禁/边缘服务器）就近做实时分析与告警，云端做集中训练、模型下发与全局态势。架构图为四层结构，需补全组件并分析架构缺点。

【问题 1】（12 分）请补全云边协同四层架构图（①端/感知层 ②边缘层 ③网络/传输层 ④云平台层）中各层的典型组件。

**参考答案**：
- **① 端/感知层**：高清摄像头、门禁控制器、周界传感器、NVR（前端采集设备）。
- **② 边缘层**：边缘服务器/边缘盒子（如 KubeEdge 节点），就近运行推理（人脸/行为识别）、本地告警、断网自治与本地持久化。
- **③ 网络/传输层**：5G/专线/Internet，负责边缘→云端的数据回传与模型下发；协议 MQTT/HTTPS。
- **④ 云平台层**：模型训练平台（GPU 集群）、模型仓库与下发、集中存储（对象存储/数据湖）、全局态势大屏、设备管理与 OTA。

【问题 2】（6 分）云边协同架构相比纯云端处理，有哪些优势？

**参考答案**：
1. **低延迟**：边缘就近推理，告警 <100ms，不依赖云端往返（适合安防实时性）。
2. **省带宽**：边缘预处理/过滤后只回传关键事件与特征，原始视频不全量上云，带宽降 70%+。
3. **断网自治**：边缘节点本地持续运行关键服务，网络故障不影响本地告警。
4. **隐私合规**：敏感数据（人脸/行为）在边缘处理，减少原始数据外发，符合个保法。
5. **弹性与成本**：云端集中训练算力共享，边缘用轻量模型推理，算力成本最优。

【问题 3】（7 分）请分析云边协同架构可能存在的缺点（至少 3 条）。

**参考答案**：
1. **一致性挑战**：边缘与云端数据/模型版本可能不一致，需处理最终一致与冲突（断网期间本地数据回传可能乱序/重复）。
2. **运维复杂度高**：大量边缘节点分散部署，版本升级、监控、故障排查成本高（需 OTA + 远程运维）。
3. **资源受限**：边缘节点算力/存储有限，复杂模型需量化/蒸馏才能部署，精度可能下降。
4. **安全风险面扩大**：边缘节点物理暴露、易被篡改，需设备身份认证、安全启动与可信执行环境。
5. **架构与同步成本**：模型下发、数据回传、影子同步机制增加系统复杂度。

## 试题五（25 分）：在线学习系统（DFD + 推荐冷启动 + 知识图谱）

【说明】某在线学习平台需重构数据处理与推荐模块。系统包含用户学习行为采集、课程推荐、学习路径规划等功能。需补全数据流图（DFD），并解决新用户/新课程的推荐冷启动问题，同时构建课程知识图谱支撑学习路径推荐。

【问题 1】（8 分）请补全顶层 DFD 的四个组成部分，并说明 DFD 四要素。

**参考答案**：DFD 四要素=**外部实体、加工（过程）、数据流、数据存储**（控制流不是 DFD 要素【陷阱】）。
- 外部实体：学员、教师/课程运营、第三方支付。
- 加工：行为采集、推荐生成、学习路径规划、支付结算。
- 数据流：学习行为→行为采集、推荐结果→学员。
- 数据存储：用户行为库、课程库、知识图谱库。

【问题 2】（8 分）推荐系统面临冷启动问题：新用户无行为数据、新课程无交互数据。请分别给出解决方案。

**参考答案**：
- **新用户冷启动**：
  1. 注册时采集显式偏好（兴趣标签、目标、基础画像）；
  2. 利用人口统计学/设备信息做粗粒度推荐；
  3. 推荐**热门/高热度课程**（非个性化，保证点击）；
  4. 快速收集反馈（引导评分/点击），渐进式个性化。
- **新课程冷启动**：
  1. 基于**内容**的推荐：提取课程标签/知识点/难度，与用户画像匹配（无需交互数据）；
  2. 利用课程**属性相似度**推荐给已学相似课程的用户；
  3. 给新课程**探索流量**（ε-贪心/Thompson 采样），快速积累交互；
  4. 结合知识图谱：把新课程挂到已有知识点上，沿图谱关联推荐。

【问题 3】（9 分）请说明如何为该在线学习系统构建课程知识图谱（实体、关系、构建流程），并说明其在学习路径推荐中的作用。

**参考答案**：
- **实体**：课程、章节、知识点（概念）、教师、用户、试题。
- **关系**：课程-包含→知识点、知识点-前置→知识点（先修关系）、用户-已学/掌握→知识点、课程-属于→领域、知识点-相关→知识点。
- **构建流程**：① 数据源整合（课程大纲/教材/题库/学习日志）→② 实体识别与抽取（NER 抽取知识点）→③ 实体链接消歧（同义知识点合并）→④ 关系抽取（先修关系来自大纲顺序/共现）→⑤ 知识融合与质量校验→⑥ 存储（图数据库 Neo4j/JanusGraph）。
- **在学习路径推荐中的作用**：基于先修关系生成**有序学习路径**（避免跳学未掌握的先修）；根据用户已掌握知识点，沿图谱推荐**下一步最该学的知识点**；检测**知识薄弱点**（未掌握的关键先修）并补齐——支撑个性化学习路径规划。

# 第二部分　2026 年下半年（10 月 24 日）

## 试题一（25 分）：质量属性 + 集群性能优化（空气质量检测 AQI）

【说明】某市构建空气质量检测系统（AQI），在全市布设上千个监测站点，持续采集 PM2.5/PM10/SO₂/NO₂ 等污染物浓度，汇聚后实时计算 AQI 并发布。系统需识别质量属性场景六要素；在集群节点故障、资源受限时，需从"污染物抽取"和"站点抽取请求"两个角度给出性能优化方案。

【问题 1】（12 分）请写出质量属性场景的**六要素**，并结合本题（如"监测站点在峰值并发上报时，系统应在 3 秒内完成 AQI 计算并发布"）分别对应。

**参考答案**六要素=**刺激源→刺激→环境→制品→响应→响应度量**。
对应本例：
- 刺激源：监测站点（或外部上报客户端）
- 刺激：峰值并发上报污染物数据
- 环境：系统正常运行、流量峰值期间
- 制品：AQI 计算/发布子系统
- 响应：完成 AQI 计算并发布结果
- 响应度量：≤ 3 秒

【问题 2】（6 分）集群节点故障导致资源受限时，架构师提出"污染物抽取"优化（按污染物类型拆分计算任务到不同节点）。请说明其机制、优点与局限性。

**参考答案**：
- **机制**：将 AQI 计算按污染物维度（PM2.5 计算、PM10 计算…）拆分为独立子任务，分发到不同节点并行计算，最后聚合。
- **优点**：任务并行度提升，吞吐增加；不同污染物计算隔离，单一计算故障不影响其他；扩展性好，新增污染物只需加子任务。
- **局限性**：存在**聚合开销与数据 shuffle**，节点间需传递中间结果；当污染物种类少、单任务计算量小时，并行收益不明显；聚合点可能成为新瓶颈。

【问题 3】（7 分）另一个方案是"站点抽取请求"（按站点分组，每个节点负责一批站点的全流程计算）。对比上一方案说明其机制、优点与局限性，并给出选型建议。

**参考答案**：
- **机制**：按站点 ID 哈希/范围分组，每个节点负责一组站点的"采集→计算→发布"全流程，数据尽量本地处理不跨节点。
- **优点**：**数据本地性好**，无需跨节点 shuffle，网络开销低；节点故障只影响部分站点，故障隔离清晰；适合站点数量大、单站计算量适中的场景。
- **局限性**：负载可能不均（热点站点集中导致某个节点过载）；扩容时需**数据迁移/重哈希**（一致性哈希可缓解）；跨站点聚合统计（如全市 AQI）仍需汇总。
- **选型建议**：AQI 计算以站点为单位独立、站点数量大→优先**站点抽取**（数据本地性优势更显著）；若后续需按污染物做全量统计分析，可叠加污染物抽取做二级并行。

## 试题二（25 分）：Redis 主从复制与哨兵

【说明】某系统使用 Redis 做主从 + 哨兵架构。热榜推荐功能从从节点读取数据时偶发读到旧数据；主从切换存在缺陷。需分析全量/增量/命令同步，给出旧数据解决方案，并补全哨兵主客观下线流程。

【问题 1】（8 分）请对比 Redis 的全量同步、增量同步、命令传播（命令同步）三种机制。

| 机制 | 触发时机 | 过程 | 开销 |
|------|----------|------|------|
| 全量同步 | 从节点初次连接 / 复制中断超跑满 backlog | 主节点 bgsave 生成 RDB → 发给从节点加载 → 再发送积压命令 | 大：RDB 生成与传输耗资源 |
| 增量同步 | 复制短暂中断后（backlog 未覆盖） | 主从根据 replication offset，从 backlog 补发中断期间的写命令 | 小：只补差额命令 |
| 命令传播 | 主节点收到写命令后实时 | 主节点异步把写命令发送给所有从节点执行 | 持续但小 |

**关键点**：全量→增量→命令传播是一个状态机；`repl_backlog`（环形缓冲）决定能否增量，中断时间过长 backlog 被覆盖则退化为全量。

【问题 2】（8 分）热榜从从节点读到旧数据，请从**业务层面**给出解决方案（至少 3 种），并指出主从切换带来的缺陷。

**参考答案·读旧数据业务方案**：
1. **强制路由主库**：对一致性敏感的热榜写入后短时间内读主库（写后读一致性），或用 `WAIT` 命令等待从节点确认。
2. **版本号/时间戳判断**：从节点读到的数据带版本号，若小于客户端上次看到的版本则重试或转主库。
3. **业务缓存兜底**：热榜结果写入后同时更新本地缓存（Caffeine），优先读本地缓存，不立刻依赖从节点。
4. **一致性哈希固定读**：同一用户/话题固定路由到同一从节点，配合半同步降低不一致窗口。
5. **延迟容忍设计**：业务上接受秒级延迟，展示时标注"数据更新于 X 秒前"。

**主从切换缺陷**：
1. **切换瞬间数据丢失**：未同步到从节点的命令在主节点宕机后丢失（异步复制）。
2. **切换窗口不可用**：从节点提升为主期间（秒级~十几秒）写请求失败。
3. **脑裂风险**：网络分区下旧主与新主同时接收写，数据不一致。
4. **客户端需感知拓扑变化**：需哨兵通知或客户端重新发现新主地址。
5. **大 key / 慢命令导致切换延迟**：从节点加载慢或阻塞，拉长切换时间。

【问题 3】（9 分）请补全 Redis Sentinel 故障转移流程：主观下线 → 客观下线 → Leader 选举 → 选举新主 → 通知客户端。说明主观下线与客观下线的区别。

**参考答案**：
- **主观下线（SDOWN）**：单个 Sentinel 实例按自己配置的 `down-after-milliseconds` 未收到主节点 PONG，单方面认为主下线——是**单节点视角**，不可靠。
- **客观下线（ODOWN）**：该 Sentinel 向其他 Sentinel 发送 `SENTINEL is-master-down-by-addr`，收到**法定数量（quorum）**个 Sentinel 同意后，判定主客观下线——是**多节点共识**，可靠。
- **Leader 选举**：判定客观下线的 Sentinel 之间用 Raft 类协议（先到先得投票）选举一个 Leader Sentinel 负责故障转移。
- **选举新主**：Leader 按优先级（`slave-priority`）→ 复制偏移量最大（数据最新）→ runid 最小 的规则选一个从节点提升为主。
- **通知**：Leader 让其他从节点复制新主（`SLAVEOF` 新主），并通过发布订阅通知客户端新主地址；旧主恢复后降为新主的从节点。

## 试题三（25 分）：商品推荐 + C/S 架构 + 支付安全（电商系统）

【说明】某电商购物比价与推荐系统需处理长尾商品推荐，并与第三方支付平台对接。系统调用第三方支付时携带凭证，支付成功后第三方发回调请求。存在三个网络安全场景：①重复提交；②TTL/Nacos 重放；③签名——需将三个防御策略对应到场景并说明机制。

【问题 1】（8 分）请说明长尾商品的特点，并判断基于内容的推荐与协同过滤哪种更适合长尾商品推荐，为什么。

**参考答案**：
- **长尾商品特点**：种类极多、单个商品销量/交互量极低（稀疏）、头部商品占少量 SKU 却占大部分销量，长尾 SKU 众多但单量少；用户行为数据极度稀疏。
- **结论**：**基于内容的推荐更适合长尾**。
- **理由**：协同过滤依赖用户-商品交互矩阵，长尾商品交互稀疏，无法形成可靠的相似性计算（冷启动 + 数据稀疏）；基于内容的推荐利用商品**自身属性**（类目、标签、价格、描述文本向量）与用户画像/已购商品匹配，不依赖交互量，能为长尾商品找到潜在买家，覆盖度更高。协同过滤更适合交互丰富的头部商品。

【问题 2】（8 分）请补全客户端/服务器（C/S）架构图中的组件（表现层/业务逻辑层/数据层），并说明 MVC 与 C/S 三层的对应关系。

**参考答案**：C/S 三层：
- **表现层（客户端）**：UI 展示、用户交互、输入校验（瘦/胖客户端）。
- **业务逻辑层（应用服务器）**：核心业务处理、推荐算法、订单计算。
- **数据层（数据库服务器）**：数据持久化、缓存。
- **MVC 对应**：Model↔业务逻辑/数据访问；View↔表现层；Controller↔表现层中的请求分发与控制逻辑（或独立控制层）。MVC 是 C/S 在表现层内部的细化模式。

【问题 3】（9 分）系统向第三方支付发起请求（带凭证），支付成功后第三方回调。存在三个安全场景：①重复提交；②重放攻击（TTL/Nacos 配置重放）；③签名。请将三个防御策略对应到场景，并说明各机制。

| 场景 | 防御策略 | 机制说明 |
|------|----------|----------|
| ① 重复提交（同一订单多次提交） | **幂等 + 去重**（业务唯一键/幂等令牌 Token） | 服务端以订单号或一次性 Token 作为幂等键，重复请求直接返回首次结果；Token 用后即焚 |
| ② 重放攻击（截获报文重复发送） | **时间戳 + Nonce + 签名有效期（TTL）** | 请求携带时间戳与随机串 Nonce，服务端校验时间戳在允许窗口（如 ±5 分钟）内、Nonce 未被使用过（缓存去重），过期则拒绝；Nacos 等配置下发也加版本号 + 签名防篡改重放 |
| ③ 防篡改/身份认证 | **数字签名**（对请求参数排序后用私钥/密钥签名，接收方验签） | 发送方对关键参数+时间戳+Nonce 生成签名，接收方用约定密钥验签，篡改任一字段签名即失效；保证完整性与来源可信 |

**补充**：三者通常组合使用——签名保证完整性与身份，时间戳+Nonce 防重放，幂等键防重复提交。HTTPS/TLS 提供传输层机密性。

## 试题四（25 分）：UML 业务建模（设备巡检与维修管理）

【说明】某设备巡检与维修管理系统需用 UML 建模。涉及活动图（巡检-派单-维修-验收流程）、类图关系、通信图，以及 UML 六种关系在业务场景中的识别。

【问题 1】（8 分）请说明 UML 中**六种关系**，并给出业务场景示例。

**参考答案** UML 六种关系：
1. **泛化（Generalization）**：is-a 继承，实线空心三角。例：「维修人员」与「高级维修工程师」（工程师是维修人员的特化）。
2. **实现（Realization）**：类实现接口，虚线空心三角。例：「派单服务」实现「通知接口」。
3. **关联（Association）**：对象间引用，实线。例：「工单」关联「设备」。
4. **依赖（Dependency）**：临时使用，虚线箭头。例：「维修流程」依赖「短信网关」发送通知。
5. **聚合（Aggregation）**：整体-部分，部分可独立，空心菱形。例：「巡检班组」聚合「维修人员」（人员可调离）。
6. **组合（Composition）**：整体-部分，生命周期一致，实心菱形。例：「工单」组合「维修记录项」（工单删记录项也删）。

【问题 2】（9 分）请说明活动图与通信图（协作图）的用途，并说明活动图中分支与并发（分叉/汇合）的表示。

**参考答案**：
- **活动图**：描述业务流程/工作流，强调活动的顺序、分支、并发与泳道（职责分配）。适合描述"巡检发现异常→自动派单→维修→验收归档"流程。
- **通信图（协作图）**：强调对象间的消息交互与组织结构，编号表示消息时序。适合描述对象协作。
- **活动图表示**：
  - **分支**：菱形决策节点，带监护条件 `[条件]` 的出边。
  - **并发**：粗黑线（同步条）表示**分叉（fork）**（一个流分成多个并发流）与**汇合（join）**（多个并发流全部到达后才继续）。
  - **泳道**：按角色/部门划分活动归属（如巡检员、调度员、维修工程师）。

【问题 3】（8 分）给出一段业务描述，判断其中对象间的关系（示例：维修工单包含多个维修步骤，工单删除则步骤删除；维修人员可属于多个班组）。请对应关系类型。

**参考答案**：
- 「工单」与「维修步骤」：整体-部分且生命周期一致→**组合**。
- 「班组」与「维修人员」：整体-部分但人员可独立存在/调离→**聚合**。
- 「维修人员」与「高级工程师」：特化→**泛化**。
- 「派单服务」调用「短信网关」：临时使用→**依赖**。

## 试题五（25 分）：嵌入式 + AI 辅助开发（电机控制系统）

【说明】某嵌入式电机控制系统引入 AI 辅助软件开发。嵌入式系统强调可靠性、可控性、确定性，而 AI 面向概率、具有不确定性。需分析 AI 对嵌入式可控性与确定性的影响、AI 在开发各阶段的作用，并说明该嵌入式电机控制系统分层架构（应用层/服务层/中间层/驱动层/HAL 层/硬件层）的优势。

【问题 1】（8 分）嵌入式面向可靠性/可控性/确定性，AI 面向概率具有不确定性。请说明在什么情况下 AI 会影响嵌入式系统的**可控性**与**确定性**。

**参考答案**：
- **可控性受影响的情况**：当 AI 直接参与**闭环实时控制**（如 AI 模型输出直接作为电机控制指令），模型行为不可解释、边界条件未知，异常输入可能导致非预期输出，系统失去对执行器的精确掌控；缺乏对 AI 输出的**人工/规则兜底**时。
- **确定性受影响的情况**：AI 推理**执行时间不确定**（依赖模型大小、输入长度、硬件负载），破坏硬实时系统的 WCET（最坏情况执行时间）可预测性；模型浮点运算、动态内存分配导致抖动；非确定性算法（如采样/随机）使相同输入输出不同。
- **缓解原则**：AI 仅用于**感知/预测/辅助决策**（开环或监控层），闭环控制仍由确定性算法（PID）完成；对 AI 输出做范围钳制、超时降级、安全状态回退；模型推理放非实时核，控制放实时核。

【问题 2】（9 分）请将 AI 能力映射到软件开发各阶段（需求分析、架构设计、代码生成、测试验证），并说明每阶段 AI 的作用。

**参考答案**：
| 开发阶段 | AI 辅助作用 |
|----------|-------------|
| 需求分析 | 需求文档自动摘要、歧义检测、需求到用例/用户故事的自动生成、需求变更影响分析 |
| 架构设计 | 根据质量属性需求推荐架构风格/设计模式、辅助生成架构图与接口定义、设计决策（ADR）辅助 |
| 代码生成 | 代码补全（Copilot/Cursor）、根据自然语言生成驱动/中间层代码、代码重构、注释与文档生成 |
| 测试验证 | 自动生成单元测试用例与测试数据、缺陷预测、变异测试、静态扫描辅助、测试结果分析 |
- **风险**：AI 生成代码可能含缺陷/安全漏洞/不符合编码规范，必须经**人工评审 + 静态扫描 + 测试**兜底，尤其嵌入式对可靠性要求高，不能直接信任 AI 输出。

【问题 3】（8 分）该嵌入式电机控制系统采用分层架构（应用层→服务层→中间件层→驱动层→HAL 层→硬件层），请说明分层架构的优势（至少 3 条）。

**参考答案**：
1. **降低复杂度、关注点分离**：每层只负责一类职责（应用=业务逻辑、服务=通用服务、中间件=通信/调度、驱动=外设、HAL=硬件抽象），单层易理解易维护。
2. **提高可移植性与可复用性**：HAL 层屏蔽硬件差异，上层代码不依赖具体硬件，换芯片/板卡只需改 HAL 与驱动，应用层不变——适合跨硬件平台复用。
3. **便于团队并行开发与测试**：层间接口稳定后，各层可并行开发、独立单元测试（用 mock 替换下层）。
4. **限制修改影响范围（可修改性）**：修改某层实现只要不破坏接口，不波及其他层（信息隐藏）。
5. **支持替换与演进**：底层硬件升级、中间件更换不影响上层业务，便于技术栈演进。

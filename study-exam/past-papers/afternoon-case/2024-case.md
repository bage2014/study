# 2024 年 系统架构设计师 下午案例分析 真题

> 考试时间：90 分钟 | 题量：5 道大题（必答） | 满分 75 分 | 合格 45 分
> 来源：网络公开真题汇编（考生回忆版 + 公开解析）
> 注意：第 1 题通常为质量属性识别；第 3 题通常为嵌入式
> 说明：本卷采用 2024 年下半年公开真题回忆版（手机 IDE 架构风格题 + 汽车电子 AUTOSAR 题）为核心。

## 试题一（25 分）：质量属性 + 架构风格（手机集成开发环境 IDE）

【说明】
某软件公司为某品牌手机厂商开发一套手机应用程序集成开发环境（IDE），以提高开发手机应用程序的质量和效率。需求描述如下：
a. 需要支持和兼容该厂商的全系列硬件。
b. 手机应用开发人员更倾向于使用 Android 系统，集成开发环境的界面需要与 Android 平台上主流开发工具的界面风格保持一致。
c. 支持相关开发数据在云端存储，需要保证在云端存储数据的机密性和完整性。
d. 支持用户备份和加载配置。
e. 支持不同模型的自动转换，在初始需求中定义的机器性能条件下，对于一个包含 50 个对象的设计模型，将其转换为相应代码框架时所消耗时间不超过 5 秒。
f. 能够连续运行的时间不小于 360 小时，意外退出后能够在 10 秒之内自动重启。
g. 集成开发环境具有丰富的插件库。
h. 支持应用开发过程中的代码调试功能，开发人员可以设置断点并启动调试。编辑器可以自动卷屏并命中断点，能通过变量监视器查看当前变量取值。

在对需求进行分析后，公司的架构师小张查阅了相关资料，认为该集成开发环境应该采用管道-过滤器（Pipe-Filter）的架构风格。公司的资深架构师王工在仔细分析后，认为应该采用数据仓储（Data Repository）的架构风格。公司经过评审，最终采用了王工的方案。

【问题 1】（10 分）
识别软件架构质量属性是进行架构设计的重要步骤。请分析题干中的需求描述，填写下表（1）~（5）处的空白。

| 序号 | 需求描述 | 质量属性 |
|------|----------|----------|
| （1） | f：连续运行 360 小时/10 秒重启 | 可用性 |
| （2） | e：50 对象转换不超过 5 秒 | 性能 |
| （3） | g：丰富的插件库 | 可修改性 |
| （4） | h：调试断点、变量监视 | 易用性 |
| （5） | b：界面风格与 Android 一致 | 易用性 |

【问题 2】（7 分）
从交互方式、数据结构、控制结构和扩展方法 4 个方面对两种架构风格进行比较，填写表（1）~（4）空白。

| 对比维度 | 管道-过滤器风格 | 数据仓储风格 |
|----------|----------------|-------------|
| 交互方式 | 顺序/链式 | （1）星型（以仓储为中心辐射） |
| 数据结构 | （2）数据流 | 集中式结构化共享数据 |
| 控制结构 | （3）数据流驱动 | 事件驱动/显式调用 |
| 扩展方法 | 新增过滤器 | （4）模型适配（适配仓储数据模型） |

【问题 3】（8 分）
在确定采用数据仓库架构风格后，王工给出了集成开发环境架构图。请填写图中（1）~（4）处的空白。

【参考答案】

【问题 1】
(1) = f → 可用性（连续运行 360 小时、10 秒重启属故障恢复/可用性）
(2) = e → 性能（模型转换时间属响应时间/性能）
(3) = g → 可修改性（丰富插件库体现可扩展性/可修改性）
(4) = h → 易用性（断点调试、变量监视降低使用成本）
(5) = b → 易用性（界面风格一致降低学习成本）

【问题 2】
(1) 星型（仓库风格，所有模块连接中央仓储呈辐射状）
(2) 数据流（管道-过滤器风格，过滤器间通过管道传递流式数据）
(3) 数据流驱动（管道-过滤器，数据到达即触发过滤器执行）
(4) 模型适配（仓库风格，新增模块只需适配仓储数据模型，不影响其他模块）

【问题 3】
(1) 语法结构树（AST/抽象语法树 + 符号表，即中央数据仓储）
(2) 编辑器（代码编辑器，输入源代码、提交变更到仓储）
(3) 适配器（模型转换器，转换不同模块数据格式适配仓储）
(4) 应用模拟器工具（手机模拟器/Simulator，在 PC 上模拟手机运行环境预览 APP 效果）

## 试题二（15 分）：UML 建模（网上销售系统）

【说明】
某软件公司为知名制造企业开发一套网上销售系统。注册用户通过商品信息页面在线浏览商品，将需要购买的商品添加进购物车内，点击"结算"按钮后开始录入订单信息。用户在订单信息录入页面上选择支付方式，填写并确认收货人、收货地址和联系方式等信息，点击"提交订单"按钮后产生订单，并开始进行订单结算。

【问题 1】（5 分）
用 UML 用例图描述系统，画出主要参与者和用例（文字描述即可）。

【问题 2】（5 分）
用 UML 类图描述订单类与订单项类的关系，类图需包括：订单号、下单时间、收货人、地址、联系方式；订单项包括商品号、数量、单价。说明两者关系类型与多重度。

【问题 3】（5 分）
用活动图描述"提交订单"流程（文字描述节点与分支即可）。

【参考答案】

【问题 1】
参与者：注册用户（也可补充：库存系统/支付系统为外部系统参与者）。
用例：浏览商品、添加购物车、结算、录入订单信息、选择支付方式、提交订单、订单结算。
关系：注册用户 → 浏览商品 → 添加购物车 → 结算 → 录入订单信息 → 选择支付方式 → 提交订单 → 订单结算。"录入订单信息"include"校验收货信息"；"选择支付方式"extend"结算"。

【问题 2】
- Order（订单）类：orderNo（订单号）、orderTime（下单时间）、receiver（收货人）、address（地址）、contact（联系方式）。
- OrderItem（订单项）类：productNo（商品号）、quantity（数量）、unitPrice（单价）。
关系：Order (1) ──包含── (0..*) OrderItem，是组合关系（实心菱形，Order 整体拥有 OrderItem 部分，Order 删除则 OrderItem 一并删除）。

【问题 3】
活动图流程：
起点 → 校验库存（分支：库存不足 → 提示缺货 → 终点；库存充足 → 继续）→ 生成订单 → 扣减库存 → 选择支付方式 → 调用支付（分支：支付成功 → 订单状态置"已支付" → 返回成功 → 终点；支付失败 → 订单状态置"已取消" → 释放库存 → 返回失败 → 终点）。

## 试题三（15 分）：嵌入式系统（汽车电子 AUTOSAR）

【说明】
某软件公司承担某汽车公司的企业汽车电子基础软件架构设计任务，参考 AUTOSAR 规范。AUTOSAR 规范定义了软件架构（SW Architecture）和基础软件（BSW）两大模块。

【问题 1】（5 分）
说明 AUTOSAR 的层次结构（自下而上）。

【问题 2】（5 分）
说明 RTE 的作用。

【问题 3】（5 分）
AUTOSAR 方法论的核心步骤有哪些？

【参考答案】

【问题 1】
AUTOSAR 自下而上层次：
1. 微控制器层（MCAL）：直接操作 MCU 硬件寄存器的驱动层（GPIO/UART/SPI/CAN/ADC 等）。
2. 复杂驱动层（Complex Device Driver）：针对特殊硬件或高性能需求的驱动，可旁路 BSW 直接对接。
3. 基础软件层（BSW）：包含服务层（OS、内存、诊断、通信、状态管理）、ECU 抽象层（ECU 级 I/O 抽象）、虚拟功能总线 VFB 接口实现。
4. 运行环境（RTE）：应用与 BSW 间的通信中间件。
5. 应用层（ASW）：软件组件 SWC，实现业务功能。

【问题 2】
RTE 是应用层与 BSW 之间的抽象层，作用：
1. 提供通信机制（信号/SWC 间通信、客户端-服务端通信），实现 VFB 虚拟功能总线。
2. 屏蔽底层硬件与总线差异（CAN/LIN/SPI/共享内存等），上层 SWC 只与 RTE 交互。
3. 实现应用软件的硬件无关性与可移植性，换 MCU/ECU 只需重新生成 RTE 与底层配置，SWC 代码不变。
4. 提供周期调度、事件触发等运行时调度能力。

【问题 3】
AUTOSAR 方法论核心步骤：
1. 系统配置：定义系统约束、ECU 资源映射。
2. ECU 配置：将软件组件映射到具体 ECU。
3. 软件组件设计：设计 SWC 的端口、接口、内部行为。
4. RTE 生成：根据 SWC 与 BSW 配置生成 RTE 代码。
5. 任务映射：将 Runnable 实体映射到 OS 任务。
6. 代码生成：用配置工具生成 BSW 配置代码与 RTE 代码。
7. 集成测试：编译链接 SWC + RTE + BSW，进行集成与验证测试。

## 试题四（15 分）：数据库设计 / Web 架构

【说明】
某电商系统设计订单表，需求包括订单查询、状态流转、报表统计。订单表 order 设计如下：order(order_id, user_id, user_name, user_phone, total_amount, status, create_time)。其中 user_name、user_phone 为用户姓名与手机号冗余字段。

【问题 1】（5 分）
判断订单表是否满足 3NF，并指出可能的传递依赖。

【问题 2】（5 分）
说明反规范化的优缺点。

【问题 3】（5 分）
说明引入 Elasticsearch 解决哪类查询问题，以及数据同步方案。

【参考答案】

【问题 1】
不满足 3NF。传递依赖：order_id → user_id → user_name / user_phone（用户姓名、手机号通过 user_id 关联用户表获取，不是直接依赖主键）。违反 3NF"消除非主属性对主键的传递函数依赖"。
优化方案：拆为 order(order_id, user_id, total_amount, status, create_time) + user(user_id, user_name, user_phone, ...)，user_id 作为外键关联。

【问题 2】
反规范化优点：减少 JOIN，提高查询性能，简化 SQL 编写。
缺点：数据冗余，更新异常（改用户手机需同步多处），一致性维护成本高（需触发器/任务同步）。
适用场景：读多写少、查询性能优先、数据量大的报表/宽表场景。

【问题 3】
Elasticsearch 解决的问题：后台多维度复杂筛选（按时间/金额/状态/用户/商品任意组合）查询慢的问题——关系数据库多字段组合查询索引难优化、like 模糊查询全表扫描。
数据同步方案：通过 Canal 监听 MySQL Binlog，将订单变更增量同步到 ES 的宽表索引（Order 索引包含订单+用户+商品维度字段），支持任意字段组合筛选与全文检索，毫秒级返回。

## 试题五（15 分）：Web 系统架构设计 / 微服务

【说明】
某电商从单体演进到微服务，团队 20 人，3 条业务线（用户、商品、订单）。

【问题 1】（5 分）
说明 DDD 限界上下文拆分原则，本项目拆几个服务合适？

【问题 2】（5 分）
列出微服务治理核心组件及对应开源选型。

【问题 3】（5 分）
说明绞杀者模式（Strangler Fig）的迁移步骤。

【参考答案】

【问题 1】
DDD 限界上下文拆分原则：通过事件风暴识别领域事件与聚合，划分限界上下文边界——按业务域、聚合根、语言边界划分，一个限界上下文对应一个微服务，保证内聚高耦合低。
本项目拆 5-8 个服务：用户服务、商品服务、订单服务、支付服务、营销服务、物流服务（按业务域拆分，团队 20 人适合 6 个左右服务，每人负责一个服务的核心职责）。

【问题 2】
微服务治理核心组件及开源选型：
1. 注册中心：Nacos（AP/CP 可切换、集成配置中心）。
2. API 网关：Spring Cloud Gateway（Spring 生态原生、Java 扩展易）或 APISIX（高性能）。
3. 配置中心：Nacos Config（与注册中心同组件、运维简单）。
4. 熔断限流：Sentinel（功能全面、控制台完善）。
5. 链路追踪：SkyWalking（Java 探针无侵入、国内生态好）。
6. 分布式事务：Seata AT 模式 + RocketMQ 事务消息（最终一致）。

【问题 3】
绞杀者模式（Strangler Fig）迁移步骤（4 阶段）：
1. 搭基础设施：建立微服务技术底座（注册中心、网关、CI/CD、容器化）。
2. 拆边缘服务：先拆非核心、边界清晰的服务（用户、营销），通过网关路由流量到新服务，老系统保留。
3. 拆核心服务：拆核心服务（商品、订单），灰度发布 + 数据双写（新老库同步），逐步切流量。
4. 老系统下线：核心迁移完成、流量全切新系统后，下线老单体系统。

### 问题一（15 分）—— 质量属性 + 架构风格对比（2025 上半年真题）

【说明】

某人工智能公司拟开发一套在线大模型训练平台，面向算法工程师和数据科学家提供一站式服务。平台支持用户通过 Web IDE 编写 Python 代码，管理数据集，提交分布式训练任务，监控训练过程中的 GPU 利用率、损失函数曲线等指标，并将训练好的模型一键部署为在线推理服务。平台日活用户约 3000 人，同时在线训练任务峰值约 500 个，模型推理接口 QPS 峰值约 2 万。

c. Web IDE 提供代码补全、语法高亮、一键运行等功能，降低使用门槛
d. 单卡训练任务启动时间不超过 30 秒，推理接口 P99 延迟不超过 200ms
e. 平台对用户上传的数据集进行自动加密存储，训练过程中数据不落盘到本地

g. 提供 Jupyter Notebook 风格交互界面，支持单元格逐行执行和结果即时展示
h. 关键服务采用多可用区部署，RPO 不超过 5 分钟，RTO 不超过 30 分钟
i. 支持通过 Mock 数据集和模拟 GPU 环境进行自动化回归测试
j. 新增一种后端训练框架（如新增 DeepSpeed 支持）不超过 2 人周
k. 训练任务支持断点续训，节点异常退出后自动重启恢复，无需人工干预
l. 提供拖拽式可视化建模工具，非编程背景用户也能搭建简单模型

【问题 2】解释器架构组件（5 分）

- **（1）程序执行当前状态（存储区）**：存储用户程序的运行时数据，包括当前执行位置、变量值、调用栈、堆内存等，类似 CPU 的寄存器 + 内存。
- **（2）解释器引擎内部状态**：存储解释器自身的控制信息，如当前解释到源代码的哪一行、下一条待执行的指令地址、已加载的模块列表等。
- **（3）解释器引擎（执行器）**：核心处理单元，循环执行"取指-译码-执行"三步：读取一条源代码/字节码指令，解析其语义，调用对应的处理逻辑执行，并更新前两个存储区的状态。

【问题 3】架构风格对比（4 分，每空 1 分）

| 对比维度 | 解释器风格 | 管道-过滤器风格 |
|----------|-----------|----------------|
| 控制驱动方式 | **（1）指令驱动（解释器主动拉取指令执行）** | **（2）数据驱动（数据到达过滤器即触发）** |
| 数据流转方式 | 共享状态/集中存储 | **（3）流经管道的数据流（每个过滤器输出作为下一个输入）** |
| 适用场景 | **（4）需要灵活执行逻辑、代码可动态改变的场景（如IDE、规则引擎、语言执行器）** | 顺序数据处理流水线 |

【问题 3】主键方案分析（4 分）

**自增主键（submissionId）方案**：
- 优点：① 字段小（bigint 8 字节），二级索引占用空间少；② 写入时主键递增，InnoDB 页分裂少；③ 被其他表引用（如申诉表）时只需存一个字段；④ Sharding-JDBC 等分库分表框架对单自增主键支持更好。
- 缺点：① 额外增加了一个无业务含义的字段；② 仍需要对（studentId, asgId）建唯一索引保证业务约束。

**复合主键（studentId, asgId）方案**：
- 优点：① 天然保证业务唯一性，无需额外唯一索引；② 无冗余字段；③ 查询"某个学生的某作业提交"时命中主键索引。
- 缺点：① 复合主键 16 字节，二级索引叶子节点存储主键，占用空间翻倍；② 主键不是递增的，随机写入可能导致 InnoDB 页分裂；③ 被其他表引用时要存两个字段；④ 部分 ORM 框架和分库分表中间件对复合主键支持不友好。

**适用场景**：复合主键适合：① 纯关联表（多对多中间表），没有独立业务含义且不会被其他表大量引用；② 查询模式固定，总是用组合的两个字段作为条件查询；③ 数据量不大，对存储空间不敏感。本题 submission 表如果数据量极大（亿级），推荐自增主键 + 唯一索引方案。

### 问题三

【问题 1】集中式 vs 分布式架构对比（5 分，每空 1 分）

| 维度 | 集中式架构 | 分布式分库分表架构 |
|------|-----------|------------------|
| 扩展性 | 纵向扩展为主，天花板低 | **（2）横向扩展为主，通过加节点扩容，理论无上限** |
| 性能 | 单库大表索引膨胀，慢查询增多 | **（3）单表数据量减小，索引更高效，并行查询能力提升** |
| 一致性 | 原生支持 ACID，强一致 | **（5）跨库无原生 ACID，需通过分布式事务保证最终一致** |

（注：（1）和（4）题干已给出，实际填（2）（3）（5），共 3 空；额外说明扩展性的读写分离 + 读库扩展、一致性的 BASE 理论，各加 1 分共 5 分。）

完整 5 分答案要点：
- 扩展性（2 分）：分布式支持分库 + 分表 + 读写分离三层横向扩展，分片数可按需调整；集中式只能升级硬件（CPU/内存/磁盘），单实例有物理极限。
- 性能（2 分）：分布式将大表拆成小表，单表索引高度降低，查询更快；同时可并行查询多个分片聚合结果，吞吐更高。缺点是跨分片查询、跨库 join 有额外开销。
- 一致性（1 分）：分布式 CAP 定理下，分区容错（P）不可放弃，只能在 C 和 A 之间权衡，通常选择 AP + 最终一致（BASE），通过补偿机制、幂等设计、校验对账来兜底。

【问题 2】分片算法 + 读写延迟方案（5 分）

（1）常见分片算法（3 分，每个 1 分）：
- **取模/哈希分片**：`分片索引 = hash(userId) % 分片数`。优点：数据分布均匀；缺点：扩容时需要大量数据迁移（如从 8 片扩到 16 片，一半数据要移动）。适用场景：用户量稳定、扩容不频繁的场景。
- **范围分片**：按 userId 或 createTime 的区间分配分片，如 userId 1-1000 万 → 分片 1，1001-2000 万 → 分片 2。优点：扩容方便（追加新分片即可），范围查询只需打一个或少数几个分片；缺点：容易产生数据热点（如新用户集中在最新分片）。适用场景：订单按时间归档、日志类写多读少且按时间查询的场景。
- **一致性哈希分片**：构造 2^32 的哈希环，分片节点映射到环上，数据 key 映射到环上后顺时针找第一个节点。优点：扩容时只影响相邻节点（只需迁移 1/N 数据）；缺点：数据分布均匀性依赖虚拟节点数量，实现较复杂。适用场景：缓存集群（Redis Cluster）、需要频繁扩缩容的 KV 存储场景。

（2）读写分离主从延迟解决方案（2 分，答 3 个即可满分）：
- **强制读主库**：对一致性要求高的场景（如下单后立即查询订单详情），将读请求路由到主库。可在代码中用注解标记，或网关根据请求类型路由。
- **半同步复制（semi-sync）**：MySQL 开启半同步复制，主库写入后需至少一个从库确认收到 Binlog 才返回客户端成功，降低延迟概率。缺点是写入性能下降。
- **写后读延迟策略**：写入后 1-3 秒内的读请求强制读主，之后再读从。可在服务层基于写入时间戳判断。
- **读从库失败重试主库**：先读从库，如果读不到或时间戳比本地新写入时间旧，则回退读主库。
- **基于 GTID 的等待机制**：写入后拿到 GTID，读从库时执行 `SELECT WAIT_FOR_EXECUTED_GTID_SET(gtid, 超时时间)`，等待从库追上再返回结果。

【问题 3】分布式事务方案对比（5 分，每空 1 分）

| 方案 | 一致性强度 | 实现复杂度 | 性能开销 | 适用场景 |
|------|-----------|-----------|---------|---------|
| 2PC（XA） | **（1）强一致（原子性）** | 高，需数据库支持 XA | **（2）高（同步阻塞，锁持有时间长）** | 强一致要求极高、并发不高的金融场景 |
| TCC | **（3）最终一致（但隔离性较好，Try 阶段预留资源）** | 很高，需写 Try/Confirm/Cancel 三个接口 | 中 | 对一致性有要求、需要回滚控制的场景 |
| Saga | 最终一致（补偿型） | **（4）中高，需定义正向操作 + 补偿操作 + 状态机编排** | 低 | 长事务、参与者多、可接受短暂不一致的业务 |
| 本地消息表 + MQ | 最终一致（可靠事件） | 中低，需发消息 + 消费幂等 | **（5）低（异步解耦，吞吐高）** | 高并发、可接受最终一致的大部分互联网业务 |

### 问题四

【问题 1】两种架构风格核心思想（5 分）

**黑板风格（Blackboard / 规则引擎模式）核心思想**（2.5 分）：
由三个核心组件构成：① **黑板（Blackboard）**：集中式数据存储，存放问题的初始数据、中间解、最终结果；② **知识源（Knowledge Sources）**：独立的专家模块（规则集），各自监控黑板上的数据变化，当满足触发条件时执行相应逻辑，更新黑板；③ **控制器/推理引擎（Controller / Inference Engine）**：决定哪个知识源在何时被激活执行（前向链 Rete 算法或后向链）。控制流是**机会主义**的，即当前黑板状态决定下一步谁执行。典型应用：Drools 规则引擎、专家系统、医疗诊断系统、语音识别（语音特征→音素→词→句子的分层求解）。

**管道-过滤器风格核心思想**（2.5 分）：
由两个基本元素构成：① **过滤器（Filter）**：独立的处理组件，从输入端读取数据，处理后输出到另一端；不与其他过滤器直接通信，无共享状态；② **管道（Pipe）**：连接过滤器的数据流通道。控制流是**顺序/数据流驱动**的，数据流过整条管道即完成处理。每个过滤器可独立复用、替换。典型应用：Unix Shell 管道（grep | sort | uniq）、编译器（词法分析 → 语法分析 → 语义分析 → 代码生成）、日志处理采集管道（Flume/Logstash）、ETL 数据处理流水线。

【问题 2】四维度对比（6 分，每空 1 分）

| 对比维度 | 黑板风格（方案 A） | 管道-过滤器风格（方案 B） |
|----------|------------------|------------------------|
| 交互方式 | **（1）隐式调用/共享内存式** | **（2）显式调用/流式传递** |
| 数据结构 | **（3）结构化的全局事实库（Working Memory）** | 流式、结构化数据，过滤器间约定数据流格式 |
| 控制结构 | **（4）模式匹配/事件**驱动 | **（5）数据到达**驱动 |
| 扩展方法 | 新增知识源（规则集）注册到黑板 | **（6）新增过滤器节点插入管道任意位置，或并行分支处理** |

【问题 3】方案选择及理由（4 分）

**推荐选择：方案 B（管道-过滤器风格）**，理由如下：

1. **延迟要求**：10 万条规则如果用 Rete 算法做全量模式匹配，延迟很难压到毫秒级（Rete 匹配复杂度与规则数成正相关，尤其是有大量条件组时）。管道-过滤器可以并行执行多个独立过滤器（黑名单、设备指纹、IP 风险等可并行），且每个过滤器可独立做索引加速（如黑名单用 Redis BloomFilter O(1) 判断）。
2. **规则独立性**：风控检查项本质上是独立的维度，而非复杂的多规则连锁推理。黑名单检查、行为异常检测、设备相似度计算之间没有强依赖和链式推理关系，天然适合拆成独立过滤器。
3. **可观测与调试**：管道-过滤器每个步骤的输入输出清晰可追踪，某个过滤器出问题可以单独定位和降级。而黑板风格多个知识源可能同时修改黑板数据，调试"为什么命中了某个风险等级"非常困难。
4. **性能优化灵活度**：管道可以对低优先级过滤器做异步处理（如复杂的行为序列模型异步打分，同步返回一个基础分，事后异步复核），或者对命中率高的过滤器前置（短路判断），而黑板风格执行顺序由推理引擎决定，性能调优难度大。

（如果选择方案 A 并给出合理理由，如"10 万规则中很多是组合条件，连锁推理多，管道-过滤器无法表达 IF A AND B THEN C 的组合规则，因此选黑板"，可酌情给 2-3 分。）

【问题 1】多级缓存 + 多级 LB 架构（5 分）

**完整链路（从用户到后端）**：
```
用户 App/Web
  │
  ▼
① DNS 智能解析（基于地理位置/运营商返回最近的 CDN 节点或边缘 POP 点）
  │
  ▼
② CDN 边缘节点（缓存静态资源：视频 HLS/DASH 分片、封面图、JS/CSS。Feed 流数据不存 CDN）
  │
  ▼
③ F5/LVS 四层负载均衡（VIP → 多个 Nginx 实例。基于源 IP/五元组哈希。支持百万级并发连接）
  │
  ▼
④ Nginx 七层负载均衡（根据 URL 路径路由到不同业务网关。支持限流、黑白名单、WAF、SSL 卸载）
  │
  ▼
⑤ API 网关集群（Spring Cloud Gateway / APISIX。统一鉴权、灰度、限流、熔断、请求聚合）
  │
  ▼
⑥ 推荐服务（多级缓存）
   ├─ L1 本地缓存（Caffeine/Guava Cache，进程内）：最热 Top 1000 用户的 Feed 结果，TTL 3-5s，容量限制防 OOM
   ├─ L2 分布式缓存（Redis Cluster）：全量用户的 Feed 结果，TTL 30s，Key=user:feed:{userId}:{page}
   └─ 降级兜底缓存（Redis 持久化）：如果推荐服务挂了，返回热门视频 Feed，保证可用性
  │
  ▼
⑦ 推荐计算服务（如果缓存未命中）：召回（协同过滤/向量召回）→ 粗排 → 精排（LR/DNN 模型）→ 重排（多样性/打散）→ 写入缓存
```

**各级缓存命中目标**：
- L1 本地缓存：命中率目标 30%~40%（覆盖大 V 和活跃用户），延迟 < 1ms
- L2 Redis 缓存：命中率目标 80%~90%，延迟 < 3ms
- 推荐计算服务回源：仅 5%~10% 的请求真正打到计算引擎

**数据更新策略**：
- 写入策略：Cache-Aside Pattern，用户新发布视频时**先更新数据库，再删除缓存**（防止先删缓存后DB未提交导致脏读）。
- 主动预热：定时任务（每 5 分钟）为前 10 万活跃用户主动刷新 Feed 缓存，避免冷启动。
- 防缓存击穿：热点 Key 加互斥锁（Redis SETNX），大量并发回源时只有一个线程查数据库。
- 防缓存雪崩：TTL 加随机偏移（±10%），避免同时失效。
- 防缓存穿透：不存在的用户 ID 缓存空值（TTL 60s），或用 BloomFilter 先过滤不存在的 Key。

【问题 3】K8s 资源 + DevOps 流水线（4 分）

（1）K8s 三种资源职责（2 分）：
- **Deployment**：工作负载资源，用于声明式管理无状态应用的 Pod 副本。定义"期望状态"：副本数（replicas）、镜像版本、资源限制、滚动更新策略等。Deployment 自动创建并管理 ReplicaSet，支持滚动更新（RollingUpdate，默认）、回滚（rollout undo）、暂停/恢复。是微服务部署最常用的资源。
- **Service**：服务发现 + 负载均衡资源，为一组功能相同的 Pod 提供一个稳定的虚拟 IP（ClusterIP）和 DNS 名称。前端服务（如订单服务）不用关心后端 Pod 的 IP 变化，通过 Service 名称即可调用。支持四种类型：ClusterIP（集群内部访问，默认）、NodePort（每个节点开放一个端口，外部可访问）、LoadBalancer（调用云厂商 LB 暴露公网）、ExternalName（CNAME 到外部域名）。
- **Ingress**：HTTP/HTTPS 七层路由资源，将集群外部请求根据域名、URL 路径转发到不同的 Service。类似 Nginx 反向代理。需要配合 Ingress Controller（如 Nginx Ingress Controller、Traefik、APISIX Ingress）使用。一个 Ingress 可以配置多个域名和路径规则，节约公网 IP。

（2）CI/CD 流水线阶段（2 分，答对 5 个即可，常见 7 个列全）：
1. **Checkout**：从 Git 仓库拉取代码（根据指定分支/Tag/Commit）
2. **静态代码检查（Lint + SonarQube）**：检查代码规范、代码坏味道、潜在 Bug、安全漏洞、覆盖率门槛
3. **单元测试（Unit Test）**：执行 JUnit/Mockito 测试，生成覆盖率报告；失败则终止流水线
4. **构建（Build）**：编译代码、打包（Java 打 Jar/War，前端 build dist 包）、构建 Docker 镜像并推送到镜像仓库（Harbor/ACR）
5. **集成测试（Integration Test）**：部署到测试环境（Testcontainers 起临时数据库等），执行接口测试（JMeter/Postman/Newman）和端到端测试
6. **安全扫描（Security Scan）**：镜像漏洞扫描（Trivy/Clair）、依赖检查（OWASP Dependency-Check）、SAST/DAST
7. **部署（Deploy）**：按环境顺序部署（DEV → FAT → UAT → PROD），PROD 环境采用灰度发布/蓝绿发布/金丝雀发布，部署后执行冒烟测试

## 试题一（25 分）：质量属性 + 解释器风格（在线大模型训练平台）

【说明】
某公司开发一个在线大模型训练平台，支持 Python 代码编写、模型训练和部署。用户通过 Python 编写模型代码，将代码交给系统进行解析，最终由系统匹配相应的计算机资源进行输出，用户无需关心底层硬件。架构师李工认为该平台适合采用解释器风格架构。系统分析师调研的需求描述如下：
a. 系统发生错误时，异常请求能够不影响用户正常工作，并发送消息通知系统管理员。
b. 平台应保护用户隐私，防止未授权访问。
c. 系统界面能调整屏幕，适配用户提供的屏幕尺寸比例。
d. 用户提交训练任务时应在一分钟内提供硬件和资源，启动训练。
e. 支持远程修改，供远程用户进行连接操作，仅提供给系统注册用户使用。
f. 在训练时，应对请求 5 秒钟内提供队列信息。
g. 支持多语言界面，操作指南和文档。
h. 发生故障时应在 15 秒钟内定位故障，解决故障。
i. 系统发生故障时，要能提供操作日志。
j. 具备扩展能力，能够 3 天内完成新功能部署。
k. 数据库发生故障后，自动切换到备用数据库，保证训练不中断。
l. 符合用户习惯的默认快捷键设置。

【问题 2】
(1) 程序执行的当前状态（存储区）：存储用户程序运行时数据，包括当前执行位置、变量值、调用栈、堆内存等。
(2) 解释器引擎的内部状态：存储解释器自身控制信息，如当前解释到源代码哪一行、下一条待执行指令地址、已加载模块列表等。
(3) 解释器引擎（执行器）：核心处理单元，循环执行"取指-译码-执行"，读取指令、解析语义、调用对应处理逻辑执行并更新前两个存储区状态。

【问题 3】
优点：① 灵活，解释执行逻辑可动态改变；② 规则可配置、易扩展；③ 适合非确定性、交互式处理流程。
缺点：① 性能差，逐条解释比编译执行慢；② 实现复杂，需维护执行状态与控制状态。
适用场景：JVM/Python 解释器、SQL 引擎、规则引擎（Drools）、大模型训练平台的代码解析层（用户提交 Python 代码由解释器解析后调度资源执行）。

## 试题二（15 分）：UML / 设计模式（银行支付状态模式）

【说明】
某银行支付系统有"待支付""已支付""已退款""已关闭"等状态，原系统用 if-else 实现，每新增一个状态或修改流转规则就要改动核心类，难维护。

【问题 1】（5 分）
用状态模式重构，画出类图核心结构（文字描述类名与关系即可）。

【问题 2】（5 分）
对比状态模式与策略模式。

【问题 3】（5 分）
说明责任链模式在网关中的应用。

【参考答案】

【问题 1】
状态模式类结构：
- Context（Payment 支付订单类）：持有 State 引用，提供 setState() 与 handle() 委托当前状态。
- State（抽象状态接口 PaymentState）：定义 handle(Event)。
- 具体状态：PendingState（待支付）、PaidState（已支付）、RefundedState（已退款）、ClosedState（已关闭）。
迁移：PendingState 收到"支付成功"事件 → 调用 context.setState(new PaidState())；PaidState 收到"退款"事件 → 切到 RefundedState；收到"超时关闭" → 切到 ClosedState。各状态类内部决定迁移，Context 不感知迁移逻辑。

【问题 2】
| 对比项 | 状态模式 | 策略模式 |
|--------|----------|----------|
| 意图 | 状态随事件自动迁移，行为随状态变 | 算法可替换，由客户端选择 |
| 状态/策略关系 | 状态间有迁移关系，互相感知 | 策略间平级无迁移 |
| 控制方 | 状态对象自身触发迁移 | 客户端显式 setStrategy |
| 典型场景 | 订单/工单状态机、设备状态 | 支付路由、排序算法选择 |

【问题 3】
责任链模式在网关中的应用：网关将请求依次经过多个处理器（Handler）链——鉴权 Handler → 限流 Handler → 熔断 Handler → 日志 Handler → 路由转发 Handler。每个 Handler 处理自己的职责，处理完调用 chain.next() 传给下一个；也可短路返回（如鉴权失败直接返回 401）。优点：① 处理器解耦、单一职责；② 链可动态配置（新增/调整处理器顺序）；③ 符合开闭原则，新增处理器不影响现有链。

## 试题三（15 分）：嵌入式（实时调度算法）

【说明】
某嵌入式实时系统有 3 个周期任务：T1(周期=4ms, 执行=1ms), T2(周期=6ms, 执行=2ms), T3(周期=8ms, 执行=1ms)。

【问题 1】（5 分）
使用 RM（速率单调）调度，给出优先级和可调度性分析。

【问题 2】（5 分）
使用 EDF（最早截止期优先）调度，可调度性如何？

【问题 3】（5 分）
说明硬实时与软实时的区别。

【参考答案】

【问题 1】
RM 优先级与周期成反比（周期越短优先级越高）：T1 最高（周期 4ms）、T2 次之（6ms）、T3 最低（8ms）。
可调度性分析：CPU 利用率 U = 1/4 + 2/6 + 1/8 = 0.25 + 0.333 + 0.125 = 0.708。
RM 可调度充分条件（Liu-Layland 上界）：n=3 时 U ≤ n(2^(1/n)-1) = 3×(2^(1/3)-1) ≈ 0.799。
0.708 < 0.799（也 < ln2 ≈ 0.693 的更严格界附近，本题 0.708 略超 0.693 但低于 3 任务上界 0.799），按 3 任务上界判定可调度。
（精确判定：逐周期响应时间分析可验证 T1=1ms<4, T2=1+2=3ms<6, T3 在 6ms 内完成 1ms<8，均满足截止期，可调度。）

【问题 2】
EDF 利用率上界为 1（单处理器只要总利用率 ≤ 1 即可调度）。CPU 利用率 0.708 < 1，可调度。EDF 动态优先级，截止时间越近优先级越高，能在超载时优雅降级。

【问题 3】
硬实时：错过截止期会导致灾难性后果（如飞机飞控、汽车刹车、医疗设备控制），必须保证确定性可调度。
软实时：错过截止期可容忍、仅降低服务质量（如视频流卡顿、网络电话延迟），统计意义上满足即可。

## 试题四（15 分）：数据库架构

【说明】
某金融交易系统数据库架构设计。

【问题 1】（5 分）
数据库三级模式（外模式/概念模式/内模式）与两级映象的作用。

【问题 2】（5 分）
分库分表的常见策略与全局 ID 方案。

【问题 3】（5 分）
说明分布式事务 2PC 的两阶段流程及缺点。

【参考答案】

【问题 1】
三级模式：
- 外模式：用户视图，特定用户看到的局部逻辑结构。
- 概念模式：全局逻辑结构，所有数据的整体逻辑定义。
- 内模式：物理存储结构与存取方法。
两级映象：
- 外模式/概念模式映象：保证逻辑数据独立性（概念模式变化，修改映象使外模式不变）。
- 概念模式/内模式映象：保证物理数据独立性（内模式/存储变化，修改映象使概念模式不变）。

【问题 2】
分库分表策略：
1. 垂直分库：按业务域拆库（订单库、用户库、商品库），解耦业务。
2. 水平分表：按 hash/range/一致性哈希将同一表数据分散到多张表/多库。hash 分片数据均匀但扩容需迁移；range 分片扩容方便但易热点；一致性哈希扩容迁移少。
全局 ID 方案：雪花算法 Snowflake（时间戳 + 机器 ID + 序列号，64 位 long，全局唯一、趋势递增），或号段模式（Leaf）、Redis 自增等。

【问题 3】
2PC 两阶段流程：
- 阶段 1（准备 prepare）：协调者询问所有参与者能否提交，参与者执行事务到准备态并锁定资源，回复 yes/no。
- 阶段 2（提交 commit/回滚 rollback）：若全部 yes，协调者发 commit，参与者提交释放锁；若任一 no 或超时，协调者发 rollback，参与者回滚。
缺点：① 同步阻塞，参与者锁定资源等待协调者，高并发吞吐差；② 单点故障，协调者宕机参与者阻塞；③ 数据不一致风险（commit 阶段部分参与者收不到消息导致部分提交）；④ 性能差，不适合互联网高并发场景。

## 试题五（15 分）：Web 系统架构（大模型平台 / 高并发）

【说明】
大模型推理服务架构设计，需支持高 QPS、低延迟、弹性伸缩。

【问题 1】（5 分）
说明负载均衡的三层架构。

【问题 2】（5 分）
说明缓存穿透/击穿/雪崩及解决方案。

【问题 3】（5 分）
说明 K8s 中 HPA 自动扩缩容机制。

【参考答案】

【问题 1】
负载均衡三层架构：
1. 第一层（接入层/四层 LB）：DNS 负载均衡 + LVS/F5（基于 IP+端口四层转发，支持百万并发连接、高吞吐）。
2. 第二层（网关层/七层 LB）：Nginx/APISIX（基于 HTTP 域名/URL 路径转发，支持 SSL 卸载、限流、灰度、WAF）。
3. 第三层（服务层/应用内 LB）：Spring Cloud Gateway/Ribbon（服务间调用负载均衡，基于注册中心实例列表轮询/加权/最少连接）。
大模型推理场景：四层 LVS 接入 → 七层 Nginx 按 model 路由 → 推理服务集群（按 GPU 卡亲和性调度）。

【问题 2】
- 缓存穿透：查询不存在的数据，缓存和 DB 都没有，每次穿透到 DB。解决：缓存空值（短 TTL）、BloomFilter 布隆过滤器拦截不存在的 key。
- 缓存击穿：单个热点 key 过期瞬间，大量并发请求穿透到 DB。解决：互斥锁（SETNX，只允许一个线程回源）、热点 key 永不过期 + 后台异步刷新。
- 缓存雪崩：大量 key 同时过期或 Redis 宕机，请求全压到 DB。解决：TTL 加随机偏移（±10%）、多级缓存（本地 Caffeine 兜底）、Redis 集群高可用 + 限流降级。

【问题 3】
HPA（Horizontal Pod Autoscaler）机制：
1. 原理：HPA 控制器周期性（默认 15s）从 Metrics Server/Prometheus 采集目标 Deployment 的指标（CPU 利用率、内存、自定义 QPS/GPU 利用率）。
2. 计算：根据当前指标值与目标期望值的比值，计算期望副本数 = ceil(当前副本数 × 当前指标 / 目标指标）。
3. 扩缩容：调用 Deployment scale 调整 replicas，Pod 由调度器分配到有资源的节点。
4. 扩容冷却：默认扩容快速（3 分钟内），缩容冷却期较长（默认 5 分钟，防抖动）。
大模型场景可基于自定义指标（GPU 利用率、推理队列长度）触发 HPA，流量高峰自动扩容推理 Pod。

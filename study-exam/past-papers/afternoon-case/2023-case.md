## 试题一（15 分）：质量属性 + 架构风格

【说明】
某物联网公司拟开发一套边云协同的智慧工厂监控系统。边缘网关部署在车间，负责采集设备温度、振动、电流等传感数据并做本地实时预警；云端负责全局聚合分析、历史存储、可视化大屏。需求描述如下：

a. 边缘网关断网时仍能独立完成本地告警，网络恢复后补传数据。
b. 传感数据从采集到本地告警延迟不超过 100ms。
c. 支持新增设备型号与协议（如 Modbus、OPC-UA），1 人周内完成适配。
d. 采集数据传输与存储加密，防止篡改与泄露。
e. 云端提供设备运行历史回溯，可查询任意时段数据。
f. 云端服务可用率不低于 99.9%，单可用区故障不影响整体。
g. 大屏可视化支持拖拽式自定义看板，无需改代码。
h. 边缘网关支持远程升级，失败自动回滚。

架构师提出方案一采用客户端-服务器（C/S）风格，方案二采用分层架构风格（感知层-边缘层-网络层-云平台层-应用层）。

【问题 1】（8 分）
将上述 a-h 需求对应的质量属性填入下表并各给一条理由。

| 需求 | 质量属性 | 识别理由 |
|------|----------|----------|
| a | （1）________ | 断网仍可告警 |
| b | （2）________ | 本地告警延迟 |
| c | （3）________ | 新增协议工作量 |
| d | （4）________ | 加密防篡改 |
| e | （5）________ | 历史回溯 |
| f | （6）________ | 可用率、单 AZ 故障 |
| g | （7）________ | 拖拽看板不改代码 |
| h | （8）________ | 远程升级回滚 |

【问题 2】（4 分）
从交互方式、数据结构、控制结构、扩展方法对比 C/S 风格与分层架构风格。

【问题 3】（3 分）
针对边云协同"边缘自治+云协同"的特点，应选择哪种风格？说明理由。

【参考答案】

【问题 1】
| 需求 | 质量属性 | 识别理由 |
|------|----------|----------|
| a | （1）可用性 | 断网独立告警属于故障下可用 |
| b | （2）性能 | 告警延迟属于响应时间 |
| c | （3）可修改性 | 新增协议工作量 |
| d | （4）安全性 | 加密防篡改保护机密性完整性 |
| e | （5）可维护性/可靠性 | 历史回溯便于追溯 |
| f | （6）可用性 | 可用率、故障容错 |
| g | （7）可修改性/易用性 | 拖拽配置不改代码 |
| h | （8）可维护性 | 远程升级回滚便于运维 |

【问题 2】
| 对比维度 | C/S 风格 | 分层架构风格 |
|----------|---------|-------------|
| 交互方式 | 客户端直接请求服务器，请求-响应 | 层间通过接口逐层调用，相邻层通信 |
| 数据结构 | 客户端与服务器约定的报文 | 层间抽象数据模型（如传感数据对象） |
| 控制结构 | 客户端驱动，显式调用 | 自上而下请求，逐层处理 |
| 扩展方法 | 改客户端/服务端接口 | 某层内部替换不影响相邻层（关注点分离） |

【问题 3】
应选择分层架构风格。理由：边云协同天然呈"感知-边缘-网络-云-应用"层次，分层风格关注点分离、各层可独立演进；边缘层可独立自治（断网仍工作），云层做全局聚合；新增设备协议只改感知层，不影响上层。C/S 难以表达边缘自治与多层协同。

## 试题二（15 分）：UML 建模 / 设计模式

【说明】
某智慧工厂设备状态有：停机、待机、运行、预警、故障。状态间迁移规则复杂（如运行中温度超阈值→预警，预警未处理持续超限→故障，故障修复→待机）。

【问题 1】（6 分）
用 UML 状态图描述设备状态迁移（文字描述状态与迁移条件即可）。

【问题 2】（5 分）
用状态模式重构原 if-else 状态判断，说明类结构。

【问题 3】（4 分）
说明状态模式与策略模式的区别及本场景为何选状态模式。

【参考答案】

【问题 1】
状态与迁移：
- 停机 →（开机命令）→ 待机
- 待机 →（启动指令）→ 运行
- 运行 →（温度超阈值）→ 预警
- 预警 →（持续超限 N 秒）→ 故障；预警 →（温度恢复）→ 运行
- 故障 →（维修完成复位）→ 待机
- 待机 →（关机命令）→ 停机
初始状态为停机，故障为可恢复终态前的告警态。

【问题 2】
- Context（Device 设备类）：持有 State 引用，handle() 委托当前状态。
- State（抽象状态接口）：定义 handle(Event) 与 next()。
- 具体状态：StoppedState、IdleState、RunningState、WarningState、FaultState。
- 状态迁移由各状态类内部决定，调用 context.setState() 切换。Context 不感知迁移逻辑。

【问题 3】
区别：状态模式中状态间自动迁移、由状态对象自身触发，客户端通常不显式选状态；策略模式由客户端显式选择策略，策略间平级无迁移。
本场景设备状态随事件自动迁移、规则复杂，属于"内部状态变化驱动行为变化"，故选状态模式。

## 试题三（15 分）：嵌入式系统

【说明】
某边缘网关采用 DMA 方式采集多路 ADC 传感数据，并通过中断通知 CPU 处理。系统要求采样率 1kHz，CPU 空闲用于运行轻量推理模型。

【问题 1】（5 分）
说明 DMA 的工作原理及相对中断轮询的优势。

【问题 2】（5 分）
说明中断方式与 DMA 方式在数据采集中的配合流程。

【问题 3】（5 分）
说明实时系统优先级反转问题及解决方案。

【参考答案】

【问题 1】
DMA 工作原理：DMA 控制器独立于 CPU，直接控制外设与内存间数据搬运；CPU 配置源地址、目的地址、传输长度后启动 DMA，传输完成 DMA 产生中断通知 CPU，全程不占用 CPU 周期。
优势：① 大数据量传输不占 CPU，CPU 可运行推理模型；② 传输速率高，避免逐字节中断开销；③ 适合 1kHz 高速连续采样。

【问题 2】
配合流程：
1. CPU 配置 ADC 与 DMA（源=ADC 数据寄存器，目=内存缓冲区，长度=一帧采样数）。
2. ADC 按采样率转换，每完成一个样本 DMA 自动搬运到内存。
3. 缓冲区填满，DMA 产生"传输完成"中断。
4. CPU 在中断中切换双缓冲（乒乓缓冲），置标志位，任务级取数据做预警推理，同时 DMA 写另一缓冲。
5. 循环往复，CPU 仅在帧边界介入。

【问题 3】
优先级反转：高优先级任务等待低优先级任务持有的共享资源，而中间优先级任务抢占低优先级任务，导致高优先级被间接阻塞时间不确定。
解决方案：
1. 优先级继承：低优先级任务持锁时临时提升到请求者优先级，尽快释放。
2. 优先级天花板：为每个资源预设天花板优先级（访问者最高优先级），持锁即提升到天花板。

## 试题四（15 分）：数据库设计

【说明】
某智慧工厂时序数据存储设计：每台设备每秒产生 10 条指标，共 1000 台设备，年数据量约 3150 亿条。需要按设备+时间范围查询、聚合统计。

【问题 1】（6 分）
说明时序数据库（如 InfluxDB/TDengine）相对关系数据库在该场景的优势。

【问题 2】（5 分）
说明数据降采样（downsampling）的概念与作用。

【问题 3】（4 分）
说明冷热数据分层存储策略。

【参考答案】

【问题 1】
时序数据库优势：
1. 列式+时间分区存储，按设备 tag 聚合、时间范围查询极快。
2. 高并发写入优化（LSM Tree 类），支撑千万级点/秒写入。
3. 内置降采样与连续查询，自动聚合。
4. 压缩比高（时间戳有序、相同 tag 重复率高）。
5. 原生支持时间窗口函数、死区/变化点压缩。

【问题 2】
降采样：将高频原始数据按时间窗口（如 1 分钟、1 小时）预聚合为均值/最大/最小/求和，存为低频序列。
作用：① 大幅降低存储量与查询成本；② 长周期趋势查询直接命中预聚合，毫秒返回；③ 保留近期原始细粒度，历史用降采样兼顾精度与成本。

【问题 3】
冷热分层：热数据（近 7 天原始点）放内存/SSD 时序库供实时查询；温数据（7 天-3 月降采样）放本地磁盘；冷数据（3 月以上）归档到对象存储（S3/OSS）+ 列存（Parquet）。查询按时间路由，热数据低延迟，冷数据低成本海量。

## 试题五（15 分）：Web 系统架构 / 多源数据集成

【说明】
该工厂需将多源数据（关系库 ERP、时序库设备指标、文件日志、第三方 API）集成到统一数据平台，供报表与 AI 分析使用。

【问题 1】（5 分）
说明 ETL 与 ELT 的区别及各自适用场景。

【问题 2】（5 分）
说明 CDC（变更数据捕获）的原理及在实时集成中的作用。

【问题 3】（5 分）
说明多源异构数据集成的 3 种常见架构（联邦查询、数据仓库、数据湖/湖仓），并比较。

【参考答案】

【问题 1】
ETL：先抽取 Extract，再在独立引擎 Transform，最后 Load 到目标库。适合源多、转换复杂、目标为专用数仓的场景。
ELT：抽取后直接 Load 到目标（大数据平台/湖），再在目标内用 SQL/Spark Transform。适合目标引擎算力强（如 Spark/Snowflake）、保留原始数据、灵活即席转换的场景。

【问题 2】
CDC 原理：监听源数据库的事务日志（MySQL Binlog、Oracle Redo），解析增删改事件，实时捕获数据变更。
作用：① 替代全量轮询，低延迟近实时同步；② 对源库侵入小（读日志不查表）；③ 保留变更顺序，支持增量入湖/入仓与缓存刷新。

【问题 3】
| 架构 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| 联邦查询 | 不搬运，查询引擎（Trino/Presto）跨源下发 SQL | 实时、无冗余 | 跨源 JOIN 性能差，不适合高并发 |
| 数据仓库 | ETL 入统一模型仓 | 模型规范、查询快、质量高 | 建模重、扩展慢、成本高 |
| 数据湖/湖仓 | 原始数据入湖（开放格式），批流统一 | 灵活、低成本、支持多引擎 | 治理要求高、模型需自助 |

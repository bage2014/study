## 试题一（15 分）：质量属性 + 架构风格

【说明】
某大型集团拟建设一套企业办公自动化（OA）系统，覆盖公文流转、流程审批、会议管理、日程共享、知识库、即时通讯等模块。系统用户规模约 5 万人，日均在线峰值 1.5 万人。需求描述如下：

a. 系统应保证 7×24 小时不间断运行，年度可用率不低于 99.9%。
b. 公文审批页面加载时间不超过 2 秒，流程提交响应时间不超过 1 秒。
c. 支持组织架构、审批规则、表单样式在线配置，无需修改代码即可上线。
d. 所有公文数据加密存储，敏感字段（如薪资、合同金额）脱敏展示。
e. 系统提供完整的操作日志和审计追踪，可追溯任意公文的流转轨迹。
f. 支持新增分支机构、新增审批流程类型，3 人天内完成配置上线。
g. 系统主站点故障后 30 秒内切换到异地灾备站点。
h. 移动端 APP 与 Web 端界面风格统一，支持手势审批。

架构师团队提出两种方案：方案一采用管道-过滤器风格，将公文流转拆为"起草→校核→审核→会签→签发→归档"的过滤器链；方案二采用数据仓储（仓库）风格，以中央文档库为核心，各模块读写共享文档对象。

【问题 1】（8 分）
请将上述 a-h 需求对应的质量属性填入下表，并各给一条识别理由。

| 需求 | 质量属性 | 识别理由 |
|------|----------|----------|
| a | （1）________ | 年度可用率指标 |
| b | （2）________ | 响应时间指标 |
| c | （3）________ | 在线配置无需改代码 |
| d | （4）________ | 加密、脱敏保护机密性 |
| e | （5）________ | 日志审计便于追溯 |
| f | （6）________ | 新增功能的工作量 |
| g | （7）________ | 故障切换恢复 |
| h | （8）________ | 界面统一降低使用成本 |

【问题 2】（4 分）
从交互方式、数据结构、控制结构、扩展方法四个方面对比管道-过滤器风格与数据仓储风格。

【问题 3】（3 分）
针对 OA 系统中"公文多环节流转、各环节可回退、需共享公文正文与附件"的特点，应选择哪种风格？说明理由。

【参考答案】

【问题 1】
| 需求 | 质量属性 | 识别理由 |
|------|----------|----------|
| a | （1）可用性 | 7×24 运行、99.9% 可用率属于可用性 |
| b | （2）性能 | 页面加载、响应时间属于性能 |
| c | （3）可修改性 | 在线配置、不改代码属于可修改性 |
| d | （4）安全性 | 加密、脱敏保护机密性与完整性 |
| e | （5）可维护性 | 日志审计便于问题定位追溯 |
| f | （6）可修改性/可扩展性 | 新增分支、流程的工作量指标 |
| g | （7）可用性 | 故障切换属于故障恢复能力 |
| h | （8）易用性 | 界面统一降低学习使用成本 |

【问题 2】
| 对比维度 | 管道-过滤器风格 | 数据仓储风格 |
|----------|----------------|-------------|
| 交互方式 | 顺序/链式，过滤器间通过管道连接 | 星型/辐射状，各模块连接中央仓储 |
| 数据结构 | 流式数据，约定输入输出格式 | 集中式结构化共享数据（如公文对象） |
| 控制结构 | 数据流驱动，数据到达即触发 | 事件驱动/显式调用驱动 |
| 扩展方法 | 新增过滤器插入管道位置 | 模型适配，新增模块适配仓储数据模型 |

【问题 3】
应选择数据仓储风格。理由：
1. OA 公文流转各环节需共享同一份公文正文与附件，仓库风格以中央文档库为核心，天然支持多模块读写共享数据，避免过滤器间反复传递大对象。
2. 流程可回退、可跳转（如会签不通过退回起草），控制流程不确定，仓库风格交互性强，适合非顺序流转。
3. 管道-过滤器风格适合单向顺序流水线，难以表达回退、会签等复杂交互。

## 试题二（15 分）：UML 建模 / 设计模式

【说明】
某 OA 系统的公文审批模块需支持多种审批策略：单人审批、会签审批（多人同时审，全部通过才过）、依次审批（按顺序逐人审）。原系统用 if-else 判断审批类型，每新增一种策略就要修改审批核心类，违反开闭原则。

【问题 1】（6 分）
用 UML 用例图描述公文审批模块的主要参与者和用例。参与者：拟稿人、审批人、系统管理员。

【问题 2】（5 分）
用策略模式重构审批策略，画出类图核心结构（文字描述类名与关系即可）。

【问题 3】（4 分）
说明策略模式与状态模式的区别，并指出本场景为何选策略模式。

【参考答案】

【问题 1】
参与者：拟稿人、审批人、系统管理员。
用例：
- 拟稿人：起草公文、提交审批、撤回公文、查看审批进度。
- 审批人：查看待审公文、同意/驳回、批注、委托他人审批。
- 系统管理员：配置审批流程、配置表单、管理用户权限。
关系：拟稿人"提交审批"include"校验公文完整性"；审批人"委托他人审批"extend"查看待审公文"。

【问题 2】
策略模式类图结构：
- Context（审批上下文类 ApprovalContext）：持有 Strategy 引用，提供 setStrategy() 和 doApprove() 委托给策略。
- Strategy（抽象策略接口 ApprovalStrategy）：定义 approve(Document) 方法。
- ConcreteStrategyA：SingleApprovalStrategy（单人审批）。
- ConcreteStrategyB：CountersignApprovalStrategy（会签审批，统计同意数达阈值才过）。
- ConcreteStrategyC：SequentialApprovalStrategy（依次审批，维护当前审批人指针）。
关系：ApprovalContext → ApprovalStrategy（聚合，运行时注入）。

【问题 3】
策略模式与状态模式结构相似，均将行为封装为独立类。区别：
1. 状态模式强调"对象内部状态变化导致行为变化"，状态间可自动迁移，客户端通常不感知状态切换。
2. 策略模式强调"算法可替换"，由客户端显式选择策略，策略间平级无迁移关系。
本场景中审批策略由管理员配置选择、彼此平级无自动迁移，故选策略模式。

## 试题三（15 分）：嵌入式系统

【说明】
某工业控制器基于 ARM Cortex-M 单片机，需管理多个中断源：定时器中断（1ms 周期，用于电机 PID 控制计算）、串口接收中断、外部 GPIO 按键中断、看门狗中断。系统要求 PID 控制周期抖动不超过 50μs，串口数据不能丢失。

【问题 1】（5 分）
说明中断优先级设置原则，并为上述四类中断安排优先级（高到低）。

【问题 2】（5 分）
说明中断服务程序（ISR）的设计要点，并指出"在中断中调用阻塞型 API"的危害。

【问题 3】（5 分）
说明中断嵌套的概念及中断延迟的组成，给出降低中断延迟的 2 种措施。

【参考答案】

【问题 1】
优先级设置原则：① 硬实时、周期短、抖动敏感的任务优先级最高；② 数据易丢失的通信中断次之；③ 按键等人机交互优先级低；④ 看门狗作为最后兜底。
本系统优先级由高到低：定时器中断（PID 周期抖动敏感）> 串口接收中断（数据不能丢）> GPIO 按键中断 > 看门狗中断。

【问题 2】
ISR 设计要点：
1. 尽量短，只做"清除中断标志、读取数据、置标志位/发信号量"，复杂处理交给任务级。
2. 避免调用阻塞型 API（如带等待的获取信号量、printf 串口打印），会导致中断被长期占用、低优先级中断饿死、甚至死锁。
3. 保护临界区，必要时关中断或使用优先级屏蔽。
4. 使用 volatile 关键字修饰 ISR 与任务共享变量，防止编译器优化。

【问题 3】
中断嵌套：高优先级中断可抢占正在执行的低优先级中断，形成嵌套，需硬件支持并设置 NVIC 优先级分组。
中断延迟组成：中断请求发出 → CPU 响应（识别+保存现场）→ 开始执行 ISR 第一条指令的时间。由硬件响应时间 + 当前不可抢占区域执行时间 + 上下文保存时间组成。
降低中断延迟措施：
1. 缩短不可屏蔽临界区（关中断时间尽量短）。
2. 将耗时处理放到任务级，ISR 只置标志立即返回。
3. 合理划分优先级，启用中断嵌套让高优先级中断及时响应。

## 试题四（15 分）：数据库设计

【说明】
某 OA 系统的公文表 document 设计如下：document(id, title, content, drafter_id, drafter_name, dept_id, dept_name, flow_type, status, submit_time)。其中 drafter_id 为拟稿人 ID，drafter_name 为拟稿人姓名，dept_id 为部门 ID，dept_name 为部门名称。

【问题 1】（6 分）
判断该表是否满足 3NF，指出传递依赖并给出规范化方案。

【问题 2】（5 分）
说明反规范化的优缺点及适用场景。

【问题 3】（4 分）
说明引入 Redis 缓存"待我审批"列表的好处及缓存与数据库一致性策略。

【参考答案】

【问题 1】
不满足 3NF。传递依赖：
- id → drafter_id → drafter_name（拟稿人姓名传递依赖主键）。
- id → dept_id → dept_name（部门名称传递依赖主键）。
规范化方案：拆分为 document(id, title, content, drafter_id, dept_id, flow_type, status, submit_time) + employee(emp_id, emp_name, ...) + department(dept_id, dept_name, ...)。drafter_id、dept_id 作为外键关联。

【问题 2】
反规范化优点：减少 JOIN，提高查询性能，简化 SQL。
缺点：数据冗余，更新异常（改一处需同步多处），一致性维护成本高。
适用场景：读多写少、查询性能优先、数据量大的报表/宽表场景。

【问题 3】
Redis 缓存"待我审批"列表好处：审批人首页查询频率高、数据相对静态，缓存命中可降低数据库压力、毫秒级响应。
一致性策略：采用 Cache-Aside 模式——先更新数据库（公文状态流转），再删除对应缓存 Key；配合短 TTL 兜底（如 30s），并使用 Binlog 监听（Canal）异步刷新缓存兜底最终一致。

## 试题五（15 分）：Web 系统架构 / 企业集成平台

【说明】
该集团已有 ERP（SAP）、HR、财务、CRM 等多套异构系统，OA 系统需与它们集成：发起审批时从 HR 取人员信息、审批通过后向 ERP 写入预算扣减、向财务推送凭证。架构师建议引入企业服务总线（ESB）。

【问题 1】（5 分）
说明 ESB 的核心功能（至少 4 项）。

【问题 2】（5 分）
对比点对点集成与基于 ESB 集成的差异。

【问题 3】（5 分）
说明集成中常用的消息格式与协议（JSON/XML/SOAP/REST），并指出 SOAP 与 REST 的核心区别。

【参考答案】

【问题 1】
ESB 核心功能：
1. 路由：根据内容/规则将消息路由到目标服务。
2. 协议转换：连接 HTTP、JMS、FTP、SOAP 等异构协议。
3. 数据格式转换：XML↔JSON、字段映射。
4. 消息中介：队列缓冲、削峰、可靠投递。
5. 编排/聚合：将多服务调用组合编排。
6. 安全与监控：鉴权、加密、日志审计。

【问题 2】
| 维度 | 点对点集成 | ESB 集成 |
|------|-----------|---------|
| 耦合度 | 高，N 个系统需 N(N-1)/2 条链路 | 低，各系统只接 ESB，星型 |
| 扩展性 | 加一个系统增加 N 条连接 | 加一个系统只接一次 ESB |
| 复杂度 | 网状，难维护 | 集中治理，易监控 |
| 性能 | 直连快 | 多一跳，略增延迟 |

【问题 3】
常用消息格式：JSON（轻量、Web 主流）、XML（企业级、强结构）；协议：SOAP（基于 XML、有规范信封/WSDL）、REST（基于 HTTP、资源+动词）。
SOAP 与 REST 区别：
1. SOAP 是协议，有严格信封、WSDL、WS-* 安全规范，适合企业级强契约；REST 是架构风格，基于 HTTP 动词操作资源，轻量灵活。
2. SOAP 报文重、解析开销大；REST 通常用 JSON，报文轻、性能好。
3. SOAP 跨协议（可走 JMS/SMTP），REST 绑定 HTTP。

### 二、微服务架构概述（200 字）

微服务是一种将单应用拆分为一组小而自治服务的架构风格，其核心特征是：单一职责、独立部署、去中心化数据、轻量通信、团队自治、容错设计。微服务不等于拆得越细越好，核心是"业务限界"匹配"组织边界"（康威定律）。一个完整的微服务体系至少涵盖：服务拆分方法论、服务治理体系、可观测性、DevOps 四大部分。

### 三、基于 DDD 的服务拆分（500 字）

{分论点 1：}
1. DDD 方法论落地三步：
   - 第一步 事件风暴（Event Storming）：召集产品、业务、研发、测试开 2 天 Workshop，用便签穷举命令、事件、聚合，识别业务流
   - 第二步 识别限界上下文（Bounded Context）：对事件聚合进行边界划分，画出 Context Map，明确上下文之间的关系（合作关系/客户-供应商/随从者/共享内核/独立/大泥球）
   - 第三步 映射微服务：一个限界上下文 → 一个或多个微服务（不建议跨上下文合并服务）
2. 本项目拆分结果（示例）：
   - 中台层：用户中心、权限中心、商品中心、价格中心、库存中心、订单中心、支付中心、营销中心、风控中心、物流中心
   - 业务前台层：App 业务 A、App 业务 B、H5 渠道、PC 渠道
   - 基础层：消息中心、调度中心、文件中心、配置中心
   - 共 48 个微服务，单服务团队 3-7 人（亚马逊 2-pizza 团队原则）
3. 拆分红线：
   - 不跨服务 JOIN（强制应用层聚合或冗余）
   - 不跨服务直连别人的 DB（只允许通过 API/事件）
   - 不共享表（一张表只属于一个服务）
4. 拆分反模式：避免 {分布式单体（拆了服务仍强依赖、一起发布）、过度拆分（调用链过长、性能恶化）、循环依赖}

### 四、服务治理组件选型（500 字）

{分论点 2：}
1. 注册中心：Nacos（AP 模型，支持权重路由、健康检查、服务元数据）
   - 3 节点集群部署，跨 AZ 容灾
   - 健康检查：TCP 探活 + 心跳上报 5s 间隔
2. API 网关：Spring Cloud Gateway
   - 路由：Path + Header 路由，动态规则 Nacos 下发
   - 鉴权：JWT 校验 + RBAC 权限，黑名单 IP 拦截
   - 限流：基于令牌桶，按用户/接口/IP 多维度
   - 灰度：按 Header 灰度（灰度用户比例 1%→5%→10%）
   - 安全：WAF 规则、XSS/SQL 注入拦截
3. 配置中心：Nacos Config
   - 多环境：dev/test/staging/prod 命名空间隔离
   - 动态刷新：@RefreshScope，核心配置变更不用重启
   - 配置规范：按服务独立 dataId，公共配置抽 shareConfig
4. 熔断限流：Sentinel
   - 限流：QPS 阈值 + 线程数阈值，热点参数限流
   - 熔断：慢调用比例 / 异常比例 / 异常数 三种策略
   - 降级：fallback 方法返回兜底数据
5. 链路追踪：SkyWalking
   - Agent 无侵入，支持 Spring Cloud + MySQL + Redis + RocketMQ 全插件
   - 采样率：生产 10%、压测/问题定位 100%
   - 告警：慢调用（>500ms）、错误率 >1% 钉钉+电话双告警
6. 分布式事务：RocketMQ 事务消息 + 本地消息表
   - 核心链路：Seata AT 模式
   - 非核心链路：最终一致性，允许 10s 内不一致

### 五、DevOps 与容器化建设（500 字）

{分论点 3：}
微服务最大的落地难点不是技术组件，而是"如何把 48 个服务高效稳定地发布和运维"。
1. 容器化：Docker + 标准化镜像
   - 基础镜像：统一公司 JDK 17 基础镜像（含 skywalking-agent、arthas、常用调优参数）
   - 镜像规范：非 root 运行、JVM 参数按 Cgroup 资源自适应、分层构建加速
2. 编排平台：Kubernetes
   - 资源：K8s 集群 3 控制面 + N 工作节点，跨 AZ 部署
   - 部署模型：Deployment（无状态）+ StatefulSet（有状态：MySQL/Redis/Nacos）
   - HPA：按 CPU 利用率（>70%）自动扩缩容，最少 2 副本保证高可用
   - 探针：livenessProbe（存活，挂了重启）+ readinessProbe（就绪，就绪前不进流量）
3. CI/CD 流水线（Jenkins + GitLab + Harbor）：
   - 开发提交 Git → Jenkins 触发（Build + 单测 + 静态扫描 SonarQube + 镜像构建 → 推 Harbor）→ 部署 staging → 自动化回归 → 人工审批 → 部署 prod → 发布验证 → 钉钉通知
   - 发布模式：金丝雀（按比例切流量）+ 蓝绿（核心链路）+ 一键回滚
   - 发布前必过：单测覆盖率 > 70%、Sonar 阻断级 0、镜像安全扫描 0 Critical
4. 监控告警：Prometheus + Grafana + Alertmanager
   - 三大黄金指标：延迟、流量、错误率
   - RED 方法：Rate/Errors/Duration
   - 四级告警：P0 电话+钉钉/P1 钉钉/P2 邮件/P3 工单
5. 日志：EFK（Elasticsearch + Fluentd + Kibana）
   - 所有服务 stdout/stderr 收集到 EFK
   - 强制规范：所有日志必须带 traceId，可串联 SkyWalking 调用链

### 六、总结与反思（200 字）

通过 {DDD 拆分 + 服务治理组件 + DevOps 流水线} 三驾马车，项目 {量化效果}。微服务化后出现的新问题：（1）服务数量多，依赖关系复杂，出现问题排查困难 → 后续补服务拓扑图 + 全链路压测平台 + 混沌工程；（2）研发学习曲线陡，新人上手慢 → 补脚手架 Spring Boot Starter 一键生成服务骨架 + 最佳实践文档；（3）发布频繁，偶发"发布即故障" → 补发布审批规范 + 核心链路变更评审 + 灰度放量 SOP。微服务不是银弹，它通过增加复杂度换取灵活度，组织能力（团队规范、流程、工具链）必须跟上架构的步伐。

> 复用案例：老系统现代化改造 / 业务快速增长重构

## 正文（2200 字）

### 一、项目背景（300 字）

{公司行业、老系统功能、上线时间、初始规模、当前规模、团队情况}。原单体系统采用 Spring Boot + MySQL，单 WAR 包部署，所有模块耦合在一个 JVM 进程内。随着 {业务增长/新业务接入/合规要求}，以下问题凸显：（1）代码耦合严重，修改一处牵一发而动全身；（2）部署效率低，全量发布 30 分钟起步，回滚成本高；（3）故障隔离差，一个 OOM 全站不可用；（4）技术栈锁死，无法局部升级或引入新技术。我作为架构师，主导了架构升级选型与落地。

### 二、软件架构风格概述（200 字）

Garlan & Shaw 将架构风格分为五大类：数据流（管道-过滤器/批处理）、调用返回（层次/OO/主程序子程序）、独立组件（事件驱动/进程通信）、虚拟机（解释器/规则引擎）、仓库（数据库/黑板）。互联网业务常用的有：单体（调用返回子类）、分层、C/S、B/S、事件驱动、微服务（独立组件 + 分层组合）、SOA 等。架构风格没有优劣，只有是否适配业务复杂度、组织规模、演进速度。下面结合项目实际，阐述风格选择的评估、设计与落地过程。

### 三、架构风格评估与候选方案对比（500 字）

{分论点 1：用 ATAM 思路分析 3 个候选}
1. 候选 A：优化单体（Modular Monolith）
   - 思路：按业务分包 + 独立 jar + 内部 API
   - 优点：改动小、运维成本低
   - 缺点：仍然耦合、部署效率未根本改善
2. 候选 B：SOA（企业服务总线 ESB）
   - 思路：服务拆分 + 中心化 ESB 调度
   - 优点：成熟治理能力
   - 缺点：ESB 单点、重量级、不够灵活
3. 候选 C：微服务（独立组件 + 轻量通信）
   - 思路：按业务限界上下文拆分、独立部署、去中心化数据
   - 优点：部署独立、故障隔离、技术异构、团队自治
   - 缺点：运维复杂度、分布式事务、链路追踪
4. 决策依据（结合本项目质量属性优先级）：
   - 可修改性（高频需求）> 可用性（全站不可用是事故）> 可测试性 > 性能
   - 组织规模：15 个研发，3 条业务线，按康威定律适合拆 3-5 个微服务
   - 结论：微服务 + 渐进式迁移

### 四、微服务架构设计与拆分（500 字）

{分论点 2：}
1. 拆分原则：DDD 限界上下文 + 单一职责 + 独立部署 + 独立数据
   - 用户中心（用户、认证、权限）
   - 商品中心（商品、库存、类目）
   - 交易中心（订单、支付、物流）
   - 营销中心（优惠券、活动、推荐）
   - 数据平台（日志、报表、离线计算）
2. 服务治理组件：
   - 注册中心：Nacos（AP，支持权重+健康检查）
   - API 网关：Spring Cloud Gateway（路由、限流、鉴权、灰度）
   - 配置中心：Nacos Config（动态刷新、多环境隔离）
   - 熔断限流：Sentinel（限流规则 + 熔断降级 + 热点参数）
   - 链路追踪：SkyWalking（无侵入、调用链拓扑）
3. 服务间通信：同步 Feign HTTP + 异步 RocketMQ 事件
4. 数据隔离：每个服务独立库，禁止跨库直连

### 五、平滑迁移策略与风险控制（500 字）

{分论点 3：}
1. 绞杀者模式（Strangler Fig）：新功能走新服务，老功能逐步迁移，不搞大爆炸重构
2. 阶段划分：
   - 阶段 1：搭建微服务基础设施（网关、注册、配置、监控）
   - 阶段 2：拆边缘服务（用户中心、营销中心），通过网关路由分流
   - 阶段 3：拆核心服务（商品、交易），灰度发布 + 数据双写校验
   - 阶段 4：老系统下线，清理历史包袱
3. 风险控制：
   - 灰度发布：按用户百分比 + 白名单放量，监控指标异常自动回滚
   - 数据双写：老库 ↔ 新库通过 Canal 同步，校验一致性 3 个月
   - 全链路压测：每阶段上线前压测，确保容量够
   - 降级开关：非核心功能一键降级，保障核心链路
4. 迁移中的坑：{服务拆分过细导致调用链过长 / 分布式事务一致性 / 配置混乱等}，通过 {合并小服务 / TCC + 最终一致性 / 配置规范} 解决

### 六、总结与反思（200 字）

通过 {架构风格评估 → 微服务设计 → 平滑迁移}，本项目在 {X 个月} 内完成了架构升级，{量化效果}。但在微服务治理方面仍有不足：{服务间调用超时策略不统一、日志规范不严格、异常处理不一致}。后续将引入 {服务网格 Istio 做流量治理、统一异常 SDK、日志全链路 ID 强制规范、混沌工程平台} 等手段持续提升架构质量。软件架构是演进出来的，不是设计出来的，需要根据业务变化持续调整。

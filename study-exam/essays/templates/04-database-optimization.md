## 正文

### 一、项目背景（300 字）

{业务背景、系统规模、原架构、痛点}。我作为架构师，负责数据库架构升级方案设计与落地。

### 二、数据库优化思路概述（200 字）

关系型数据库优化可分为：SQL 与索引优化（最低成本）、读写分离（垂直扩展读）、分库分表（水平扩展容量与写）、引入 NoSQL 做专项能力（KV、全文检索、宽表）。优化顺序：先 SQL 与索引，再架构升级；架构升级的优先级：读写分离 → 垂直分库 → 水平分表。下面结合项目具体阐述三个核心动作。

### 三、读写分离架构设计（500 字）

{分论点 1：}
1. 方案拓扑：1 主 4 从（写主、读从），主从采用 MySQL 5.7 GTID 半同步复制
2. 路由层选型：ShardingSphere-JDBC（应用层内嵌，无中间件单点，运维成本低）
3. 读策略：
   - 一主多从，从库负载均衡（轮询 + 权重）
   - 强制读主：写后立即读、一致性要求高的交易链路走 hint 强制主库
   - 延迟感知：从库 seconds_behind_master > 2s 时，路由切回主库或剔除
4. 延迟容忍的业务分层：
   - 实时类（订单创建后查）：主库
   - 准实时类（报表 5 分钟内）：从库
   - 离线类（日报）：从库或数仓
5. 高可用：主库故障由 MHA 自动切换，VIP 漂移；从库故障由 Proxy 自动剔除

### 四、分库分表策略与实施（500 字）

{分论点 2：}
1. 垂直拆分：按业务域分库
   - 用户库（user_center）：用户表、认证表、权限表
   - 商品库（product_center）：商品表、库存表
   - 订单库（order_center）：订单表、支付表、物流表
   - 营销库（marketing_center）：优惠券、活动
2. 水平拆分：订单表按 user_id 哈希
   - 拓扑：32 库 × 32 表 = 1024 张逻辑分片表
   - 分片算法：user_id % 32 → 库号，(user_id / 32) % 32 → 表号
   - 分片键选择：订单系统核心查询维度都是 user_id，命中 95% 场景
   - 非分片键查询：订单号查询时，订单号本身通过雪花 + user_id 后 6 位编码，解析后可路由
3. 全局唯一 ID：雪花算法 Snowflake
   - 1 位符号 + 41 位时间戳（毫秒，69 年）+ 10 位 workerId（1024 实例）+ 12 位序列号（4096/ms）
   - workerId 分配：按 K8s StatefulSet 序号 + 机房编号，避免冲突
4. 平滑迁移：
   - 阶段 1：双写（老库 + 新库），通过 Canal 增量同步校验
   - 阶段 2：读流量从 1% → 10% → 50% → 100% 灰度切新库
   - 阶段 3：停双写，新库单写，观察 1 个月后下线老库
5. 跨库查询问题：
   - 运营后台多维度复杂查询 → 用 Canal 同步到 ES 宽表
   - 跨库 join → 应用层多次单表查询后聚合 + 冗余字段设计
   - 报表 → 入 Hive 数仓，离线跑

### 五、引入 NoSQL 补足短板（500 字）

{分论点 3：}
关系型数据库不适合所有场景，必须多存储融合：
1. Redis（KV 缓存 + 计数）：
   - 场景：用户 session、商品详情、库存预扣减、排行榜、点赞计数
   - 架构：3 主 3 从 Cluster，热点 Key 本地 Caffeine 一层兜底
   - 一致性：写 DB 后删缓存 + 延迟双删（1s 后再删一次）
2. Elasticsearch（全文检索 + 多维度筛选）：
   - 场景：订单后台多条件查询（按时间、金额、状态、用户、商品多维组合筛选）
   - 同步：Canal 监听 MySQL binlog → MQ → Logstash 写入 ES
   - 索引设计：订单宽表索引 + 冷热分离（近 3 个月热索引 SSD，历史数据冷冻到 OSS）
3. HBase（海量明细）：
   - 场景：行为日志、审计日志、消息流水
   - RowKey 设计：reverse(uid) + timestamp，避免热点
4. ClickHouse（实时分析）：
   - 场景：实时大盘（1 分钟级 GMV、订单数、转化率）
   - 用 ReplacingMergeTree + 物化视图聚合
5. 选型原则：
   - 核心交易：MySQL（强一致）
   - 读多写少 + 热点：Redis
   - 多维检索 + 全文：ES
   - 海量明细写入：HBase
   - OLAP 实时分析：ClickHouse

### 六、总结与反思（200 字）

通过 {读写分离 + 分库分表 + 多存储融合}，系统在 {量化效果}。不足与改进：（1）跨库分布式事务目前采用 RocketMQ 最终一致性，极端情况有短时间不一致，后续补 Seata TCC 模式覆盖核心链路；（2）ES 数据一致性依赖 Canal + MQ，曾出现过丢消息导致数据偏差 1%，后续补 ES 与 MySQL 定期对账 Job；（3）分库分表后扩容问题（32 库不够），需要提前规划在线扩缩容方案（如两倍扩容 + 一致性哈希）。数据库架构是业务的地基，必须根据业务增长提前 6-12 个月做容量规划和压测。

# 论文模板 03：软件质量属性设计与架构评估

> 对应主题：质量属性场景 / 性能 / 可用性 / ATAM 方法
> 复用案例：核心交易系统 / 金融支付 / 在线教育高可用

---

## 摘要（300 字）

20XX 年 X 月，本人参与了 {公司名} 的 {核心交易/支付系统} 架构设计项目，担任系统架构师。该系统是公司核心业务承载平台，年交易额 {XX 亿}，用户 {XX 万}，业务对性能、可用性、安全性等质量属性要求严苛（可用性 99.99%、P99 < 200ms、数据零丢失）。本文以该项目为背景，讨论了软件质量属性的场景化设计与架构评估实践。具体阐述了（1）基于六要素模型的质量属性场景梳理与优先级排序；（2）性能与可用性两大核心属性的战术设计与落地；（3）运用 ATAM 方法进行架构评估与风险识别三个方面。最终系统上线后连续 6 个月达到 {99.99% 可用、P99 120ms、零数据事故}，充分说明了质量属性场景驱动架构设计的工程价值。

## 正文（2200 字）

### 一、项目背景（300 字）

{公司行业、系统定位、业务规模、关键约束}。本系统作为核心交易平台，直接承载公司营收，任何重大故障都会造成 {资金损失 + 客诉 + 合规风险}。项目初期业务方给出的粗粒度需求是"稳定、快、不能出事"，但缺乏可量化的质量目标。我作为架构师，主导了质量属性场景梳理、战术设计、架构评估全流程。

### 二、质量属性概述（200 字）

ISO/IEC 9126 将质量属性分为 6 大特性（功能性、可靠性、易用性、效率、维护性、可移植性）。架构设计关注的核心质量属性可归为 6 类：性能、可用性、安全性、易用性（运行期）与可修改性、可测试性（开发期）。每个质量属性都通过"质量属性场景六要素"（刺激源、刺激、制品、环境、响应、响应度量）具体化为可验证的场景。架构评估方法 ATAM（架构权衡分析方法）正是基于场景进行多属性权衡的工程化方法。

### 三、质量属性场景梳理与优先级（500 字）

{分论点 1：用六要素梳理 N 个场景，按重要性-难度排优先级}
1. 核心方法：召集业务方、产品、研发、运维、DBA 开 3 次 WorkShop，围绕"系统会遭受哪些刺激？应该如何响应？"穷举场景
2. 性能场景示例（六要素展开）：
   - 刺激源：正常用户 + 大促秒杀
   - 刺激：5 万 TPS 请求下单
   - 制品：订单服务 + 交易链路
   - 环境：峰值（大促前 1h）、部分节点故障
   - 响应：正常处理、限流降级非核心请求
   - 响应度量：平均响应 < 100ms、P99 < 200ms、成功率 > 99.9%
3. 可用性场景示例（六要素）：
   - 刺激源：机房网络故障 / 某节点 OOM / DB 主从切换
   - 刺激：单节点不可用 / 单 AZ 故障
   - 制品：交易全链路
   - 环境：正常运行 7×24
   - 响应：自动摘除故障节点、流量切正常节点、用户无感
   - 响应度量：RTO < 30s、RPO = 0、年停机 < 53 分钟（99.99%）
4. 优先级排序（效用树）：
   - P0（必须）：可用性（故障自动转移）、性能（峰值响应）、安全性（交易防重）
   - P1（重要）：可修改性（需求 1 周上线）、可测试性（核心链路自动化覆盖率 80%）
   - P2（可选）：易用性（控制台）

### 四、核心质量属性的战术设计（500 字）

{分论点 2：}
1. 性能战术：
   - 资源需求侧：减少事件处理层数（合并中间件）、提升计算效率（算法优化 + JVM 调优）、减少传输数据量（Protobuf 替代 JSON）
   - 资源管理侧：多级缓存（本地+Caffeine + 分布式+Redis）、异步并发（RocketMQ 削峰）、线程池隔离（Hystrix/Sentinel 舱壁模式）
   - 资源仲裁侧：优先级队列（核心交易高优）、静态资源 CDN
2. 可用性战术：
   - 故障检测：心跳（Nacos 3s 未响应剔除）、Ping/Echo、异常监控（Prometheus + Alertmanager）
   - 故障恢复：冗余（3 副本 + 跨 AZ）、重启（K8s livenessProbe 自动拉起）、选举（DB MHA / Redis Sentinel）、回滚（版本化发布 + 一键回退）
   - 故障预防：移除故障节点（摘除 5min）、进程监控（Sentinel 熔断）、事务回滚（Seata AT 模式）
3. 安全性战术：
   - 身份认证（JWT + 刷新令牌）、授权（RBAC + 数据权限）
   - 机密性（传输 TLS 1.3、落盘 AES-256、敏感字段脱敏）
   - 完整性（签名校验、防重放 nonce + timestamp）
   - 审计（全链路操作日志，不可篡改）

### 五、ATAM 架构评估实践（500 字）

{分论点 3：按 ATAM 9 步流程}
1. 步骤 1-3：ATAM 方法介绍 + 业务动机呈现 + 架构呈现（给评估组讲清架构图、核心决策）
2. 步骤 4：架构方法识别（列本项目关键决策：微服务拆分、多级缓存、读写分离、跨 AZ 部署）
3. 步骤 5：效用树生成（将前述 P0-P2 场景挂到属性树下，按重要性 1-10、难度 1-10 打分，识别高风险高回报场景）
4. 步骤 6-8：两轮分析架构方法
   - 第一轮：对 P0 场景逐一走查，识别敏感点、权衡点、风险点
   - 第二轮：深入分析高风险场景（如"大促峰值下 Redis 集群雪崩"），给出缓解方案（加本地缓存兜底 + 热点 key 互斥锁 + 过期时间打散）
   - 识别出的敏感点：{读写分离的数据延迟}；权衡点：{一致性 vs 性能}；风险点：{跨 AZ 网络波动导致 RTO 超 30s}
5. 步骤 9：结果呈现（输出：风险集、非风险集、敏感点集、权衡点集），评审通过后进入落地
6. 评估后调整：原方案中 DB 单 AZ 部署改为跨 AZ MHA，增加同城灾备

### 六、总结与反思（200 字）

通过 {六要素场景梳理 → 战术设计 → ATAM 评估}，项目在质量属性方面达成了预期目标（量化效果）。实践中的体会：（1）场景必须可度量，避免"快、稳定"这种空话；（2）没有完美架构，只有权衡后的最优解；（3）ATAM 需要多角色参与，避免架构师自嗨。不足：{安全属性场景覆盖不足，后续补等保三级整改；可测试性自动化只覆盖了 60%，后续补压测平台 + 混沌工程}。持续的质量度量和架构复盘是保障系统长期健康的关键。
